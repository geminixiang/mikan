# Who owns what between the platform adapters and the core (2026-10)

Question: which responsibilities do the platform adapters (`src/adapters/{slack,telegram,discord,github}`) actually hold, which ones does the core hold, and where do the two disagree? This records the code at `fc5e4723`; it proposes nothing.

Sources: the import graph of each adapter, `src/adapters/slack/bot.ts`, `src/adapters/intake.ts`, `src/types.ts`, `src/main.ts`, `src/runtime/README.md`, and [ADR 0021](../adr/0021-tasks-as-background-child-conversations.md).

Runs are serialized again per `(OfficeAddress, sessionKey)` by `src/runtime/session-lifecycle.ts`. The adapter queue adds intake order, the ⏳ reaction, and the backlog limit.

The task rows are the largest. [ADR 0021](../adr/0021-tasks-as-background-child-conversations.md) decision 6 says "the runtime resumes a task", while `src/runtime/README.md` says "the Slack bot resumes it", and the code matches the README. Decision 8 (status and stop from pi-durable state) is not done, so the log-scanned status above is still the live path. Because the task flow lives in the Slack bot, no other platform has tasks.

## The task flow end to end

A task touches four modules. Each row is one step, in the order a task lives.

| Step                   | What happens                                                                                                                                                                                                                                               | Owner today                                                                                 |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| Offer the tools        | `start_task` is offered when the responder has `startTask`; `task_status` when it has `getTaskStatus` and the run is not a task run                                                                                                                        | Harness (`runner.ts`, `session.ts`), driven by which closures Slack sets in `createContext` |
| Start                  | The model calls `start_task`; the tool calls `responder.startTask`                                                                                                                                                                                         | Harness tool `harness/tools/task.ts`                                                        |
| Create the thread      | Delete the progress message, post the acknowledgement as the root, log it with `taskRoot: true`                                                                                                                                                            | Slack `createContext`                                                                       |
| Create the child       | `SessionStore.openTask`: one commit on the requester creates a background anchor task, a child conversation owned by it, and the session index record                                                                                                      | Sessions, called by Slack                                                                   |
| Queue the run          | `enqueueTaskRun` puts the brief on a Slack queue keyed by the task's session, with message ID `task:<root>`, and calls `handler.handleEvent`                                                                                                               | Slack                                                                                       |
| Run                    | The `task:` prefix sets `detachOnShutdown`, so shutdown neither waits for nor aborts it                                                                                                                                                                    | Runtime, from an ID prefix defined in the harness tool module                               |
| Report the result      | On a normal end, `SessionStore.reportTaskOutcome` writes the answer into the requester's transcript                                                                                                                                                        | Runtime and sessions                                                                        |
| Notify the requester   | The presenter calls `responder.notifyCompletion`, which mentions the requester in the thread                                                                                                                                                               | Harness presenter, closure from Slack                                                       |
| Status                 | `querySlackTasks`: task roots from the office log, live state from `handler.getRunningSessions()`, ended state from `SessionStore.inspectExecution`                                                                                                        | Slack `task-status.ts`                                                                      |
| Route a DM reply       | `handleMessageEvent` decides whether a message concerns tasks (thread is a task root, a task is running, or a status regex matches); `deliverTaskUpdate` asks Jev for status, steer, or request                                                            | Slack `bot.ts`, `task-intent.ts`                                                            |
| Answer status          | Fixed Chinese sentences from `formatTaskStatus`, posted without a model turn                                                                                                                                                                               | Slack                                                                                       |
| Steer                  | `handler.steer` on the task's running session                                                                                                                                                                                                              | Runtime                                                                                     |
| Stop                   | The ordinary `stop` path                                                                                                                                                                                                                                   | Intake and runtime                                                                          |
| Shut down              | Slack `stop()` does not wait for task queues; the runtime lifecycle skips detached runs                                                                                                                                                                    | Slack and runtime                                                                           |
| Abort on open          | Opening the office aborts unfinished work that has no owner and is not background                                                                                                                                                                          | Sessions                                                                                    |
| Resume after a restart | `resumeInterruptedTasks` scans Slack DM offices for task roots from the last 24 hours, asks `SessionStore.interruptedSince`, claims a resume (at most two), posts a notice, queues `resume:<root>` with `RESUMED_TASK_PROMPT` as the last human in the log | Slack, using sessions                                                                       |

What the code shows:

- **Sessions already hold the durable task.** The anchor, the ownership, the resume counter, and the run record are in pi-durable through `SessionStore`. ADR 0021 decisions 1, 4, 5, 6, and 7 are implemented there and in the runtime.
- **Which threads are tasks is recorded twice.** pi-durable knows each child and its owner; Slack finds tasks by scanning `log.jsonl` for `taskRoot` entries. Status, routing, and resume all read the log copy.
- **A task run is marked by its message ID.** `task:` and `resume:` prefixes on `ConversationEvent.ts` are how the runtime and harness tell a task run apart; the event has no task field.
- **The steps that are platform work** are creating the thread, the completion mention, and the wording of notices. Choosing what to resume, assembling status, and classifying a reply do not depend on Slack, but are written against Slack's session-key grammar and office log.
- **The requester of a resumed run** is taken as the last human in the DM's log, not from the task record. In a one-to-one DM that is always the requester; it would pick the wrong person once tasks open to channels.

## Second pass: checks and experiments

Experiments ran on a copy of a local test DM office (`sqlite3 .backup` of `sessions.db`, the live `log.jsonl` read only), with pi-durable's public API, under `.workspace/task-owner/`.

| Claim                                                        | Check                                                                                                                                 | Result                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| pi-durable can list a requester's tasks without the log      | `tx.scanConversations({ ownerConversationId })` on the DM's root conversation                                                         | Returns all 10 tasks started since the durable change, each with its session index key, in 0.1 ms                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| An owner edge means "task"                                   | Scan every conversation in the office                                                                                                 | 23 conversations: 10 have an owner, all owned by a `mikan.task-anchor` task; the one fork has no owner. Reading one conversation's owner costs 0.006 ms                                                                                                                                                                                                                                                                                                                                                                                      |
| pi-durable's live task graph shows tasks                     | Anchor task state                                                                                                                     | No. The anchor commits `terminal` in its first phase, so `inspect()` and `taskGraph()` never list it; only the conversation's owner edge remains                                                                                                                                                                                                                                                                                                                                                                                             |
| The log and pi-durable agree                                 | Compare the 46 `taskRoot` entries with the scan                                                                                       | 10 in both. 36 only in the log: 11 are ownerless thread sessions from before the durable change, and 25 have no session at all (all dated before 2026-10-04; local test data, cause not checked). Nothing is only in pi-durable                                                                                                                                                                                                                                                                                                              |
| Run status is readable from pi-durable                       | `mikan.session` doc per task                                                                                                          | Status and end time are present for every ended run. The start time is overwritten when the run ends, so only a resume claim keeps both                                                                                                                                                                                                                                                                                                                                                                                                      |
| Reading task roots is cheap                                  | `readTaskRoots` on a 0.7 MB log                                                                                                       | 2.3 ms per call, linear in log size; a DM message in a thread calls it up to twice. The ADR measured 0.1 s for a 57 MB log at startup                                                                                                                                                                                                                                                                                                                                                                                                        |
| The runtime could resume through the existing `enqueueEvent` | Read `SlackMessagingBot.enqueueEvent`                                                                                                 | Not as is: it builds the context with `createSlackAdapters`, not `createContext`, so the completion mention is lost, and the queue is not marked as a task queue, so Slack's `stop()` would wait for it                                                                                                                                                                                                                                                                                                                                      |
| `/new` and a running task                                    | Drive `SessionLifecycle` from `dist`: a run holds conversation work, `/new` asks for maintenance, then the next message asks for work | `/new` waited 3 s until the "task" released, and the next message waited behind `/new`. Every task run holds the DM's conversation work, so `/new` in a DM waits for every running task and blocks the DM until they end. Reproduced in Slack: with a task running `sleep 150`, `/pi-new` sent at 0 s reset the session at 116 s, the moment the task ended, and a message sent at 6 s started its run at 116 s with no reply or reaction meanwhile. Fixed by removing the barrier ([#158](https://github.com/geminixiang/mikan/issues/158)) |

Other paths checked:

- **Scheduled events** also create a thread (`planSlackEventAnchorRun`, `registerThreadSession`), but as an ordinary ownerless thread session; they are not tasks.
- **Other platforms and channels** never see the task tools: the runner offers `start_task` only when the responder has `startTask`, which Slack sets only for top-level DMs.
- **Session View** sends with a silent responder, so a message typed there into a task thread gets no task tools and no completion mention.
- **Concurrency**: each task has its own Slack queue and its own runtime lane per session key; tasks run in parallel with the DM's top level.

## Platform knowledge inside the core

| Fact                                                            | Where                                             | Kind                                                                            |
| --------------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------- |
| Conversation kind from ID prefixes for Slack, Telegram, Discord | `sessions/session-key.ts` `inferConversationKind` | ID format; used by the scheduler, Session View, and Slack                       |
| GitHub conversation ID codec                                    | `office/index.ts`                                 | ID format                                                                       |
| Slack auto-reply marker files and mode                          | `settings/index.ts`                               | Slack-named setting, read by Slack and `/pi-auto-reply`                         |
| `slack.replyMode` in `AgentConfig`                              | `types.ts`                                        | Slack-named setting                                                             |
| OpenConnector token name per platform                           | `harness/open-connector.ts`                       | Per-platform naming                                                             |
| Only Slack can be public                                        | `office/projection.ts`                            | Platform capability                                                             |
| Block Kit instructions added when the platform is Slack         | `harness/prompt.ts`                               | Prompt text that `MessagingInfo.formattingGuide` already carries for other text |
| `slackBlocks`, `slackInteraction` on log entries                | `types.ts`, `office/log.ts`                       | Platform payload in the shared log                                              |
| `ts`, `thread_ts`, `channel` field names on `ConversationEvent` | `types.ts`                                        | Slack vocabulary in the shared event                                            |

Some of these are deliberate: the settings file format is the core's, and the log is shared storage. Each would need its own reason to move.

## Open questions

- Should tasks (start, resume, status, routing) belong to the runtime, as ADR 0021 decision 6 states, with Slack keeping only the thread presentation?
- Should the auto-reply decision move to the runtime, with the adapter reporting only that a message was not addressed?
- Should platform ID formats move behind the adapter, for example as a method each adapter supplies?
- Should the four queue copies become one shared intake owner, given that the runtime already serializes runs?
