# Agent 長期記憶技術研究：給 Memory capture 的改進依據

**日期**：2026-10-15
**範圍**：比較各系統與論文如何決定「何時寫入、寫什麼、怎麼寫、如何去重／更新／刪除／整併、範圍、如何注入或檢索」，整理哪些技巧有量測證據，並針對 mikan Memory capture 目前的錯誤提出排序過的改進建議。
**來源規則**：每項主張都附原始來源（論文、官方文件或原始碼路徑）。標示「推論」者為本文的推斷，不是來源的說法。所有網頁與程式碼於 2026-10-15 取得；程式碼附 commit。

## 摘要

- mikan 的問題不是「記不住」，而是「記錯」：直接訊息來源的條目只有約一半正確，主要錯誤是把一次性請求寫成長期規則，以及把只有助理說過的內容寫進去（ADR 0011、mikan 內部評估）。
- 外部證據一致指出：**寫入的品質比數量重要**。在 arXiv 2505.16067 的受控實驗中，「全部寫入」在四個 agent 上都比「完全不寫入新記憶」還差，而嚴格篩選後寫入則四個都最好（見 §3.1）。
- mikan 自己的重放量測顯示，**換抽取模型的影響最大**（同一 prompt，精確率 0.23 到 0.89，依評審模型而定），加入討論串前文沒有提高精確率（§4）。
- 各家「整份注入」的系統（Claude Code auto memory、CLAUDE.md、Cursor／Windsurf rules）都對檔案大小設上限，並靠「接近上限時提醒模型合併或刪除過時條目」控制成長（§2）；以檢索為主的系統（mem0 v3）才敢只增不刪，因為由檢索負責排序。mikan 沒有檢索，所以只增不刪的設計不能照搬（推論，§3.5）。
- 建議優先順序（§5）：1. 抽取改用較強模型或提高精確度門檻（量測支持）；2. 抽取 schema 加入「使用者原話引述」與「持久性理由」欄位並以程式驗證引述；3. 短訊息與一次性請求的處理規則；4. 加入 delete 操作與使用者可見的更正路徑；5. 以 mikan 已有的標註集做離線評估，比照 MemSkill 的「失敗案例 → 改 prompt → 分數變好才保留」迴圈；6. 依大小觸發的就地整併，等量測到大小問題再做。

## 4. mikan 自己的量測（本地重放）

以下為 mikan 維護者提供的本地量測，不是外部來源。設定：從直接訊息中取 59 組來源對話，用正式環境的抽取 prompt 重放；評審為 LLM，並由人工抽查 10 個標籤，全部一致；精確率 = 產生的條目中被判為正確的比例。

**抽取模型的影響最大**（同一 prompt）：

| 抽取模型               | 精確率（評審 gpt-6.1-sol） | 精確率（評審 claude-opus-5-5） |
| ---------------------- | -------------------------- | ------------------------------ |
| gpt-6.1-sol            | 0.89                       | 0.57                           |
| gpt-5.6-terra          | 0.51                       | 0.34                           |
| gpt-6-luna             | 0.23                       | 0.23                           |
| 正式環境的直接訊息條目 | 0.56                       | 0.40                           |

兩個評審在 52–74% 的標籤上一致，因此絕對數字取決於評審，但排名相同。

**討論串前文沒有幫助**：加入最多 8 則先前的討論串訊息後，精確率 0.81 vs 不加 0.89（評審 gpt-6.1-sol）；0.58 vs 0.57（評審 opus）。

**要求引用使用者原話（§5 第 2 項）有量測支持**：抽取 prompt 加上「每條附使用者原話片段（`evidence`）與 `scope`（`standing`／`this-request`）」，並由程式丟掉引用不是使用者訊息子字串、或 `scope` 不是 `standing` 的條目。同一組 59 組來源對話：

| 抽取模型      | prompt               | 條目數 | 錯誤條目（評審 sol／opus） | 精確率（評審 sol／opus） | 至少有一條正確條目的來源數（sol／opus） |
| ------------- | -------------------- | ------ | -------------------------- | ------------------------ | --------------------------------------- |
| gpt-6.1-sol   | 正式環境             | 65     | 6／2                       | 0.78／0.60               | 41／34                                  |
| gpt-6.1-sol   | 引用原話             | 48     | 0／1                       | 0.96／0.63               | 39／27                                  |
| gpt-6.1-sol   | 引用原話＋討論串前文 | 50     | 0／0                       | 0.96／0.68               | 40／未計                                |
| gpt-5.6-terra | 正式環境             | 61     | 13／6                      | 0.51／0.34               | 28／未計                                |
| gpt-5.6-terra | 引用原話             | 46     | 3／3                       | 0.80／0.61               | 30／未計                                |

同一個 gpt-6.1-sol 正式環境 prompt 兩次重放的精確率分別為 0.89 與 0.78（評審 sol），所以單次重放有約 0.1 的雜訊。解讀：引用原話後錯誤條目幾乎歸零、精確率在兩個評審下都上升；代價是條目變少，以 opus 評審計「抓到正確知識的來源」從 34 降到 27，召回有損失。對較弱的抽取模型（terra）提升最大。

**實作後的端對端驗證**：把上述做法實作進 `src/memory-capture/index.ts` 後，用建置好的 `MemoryCapture`（改動前與改動後各一份），在同一組 59 組來源上直接跑（Jev 固定通過，只比較抽取）：

| 抽取模型      | 版本   | 寫入條數 | 錯誤（sol／opus） | 精確率（sol／opus） | 有正確條目的來源數（sol／opus） |
| ------------- | ------ | -------- | ----------------- | ------------------- | ------------------------------- |
| gpt-6.1-sol   | 改動前 | 61       | 7／3              | 0.72／0.59          | 37／29                          |
| gpt-6.1-sol   | 改動後 | 47       | 0／1              | 0.94／0.66          | 38／27                          |
| gpt-5.6-terra | 改動前 | 65       | 19／7             | 0.43／0.34          | 26／21                          |
| gpt-5.6-terra | 改動後 | 41       | 2／4              | 0.83／0.56          | 31／20                          |

兩個評審下精確率都上升、錯誤條目減少，「有正確條目的來源數」大致持平，召回沒有明顯損失。正式環境使用的抽取模型未在本地測試，以上兩個模型作為強／弱代表。

**短訊息較容易出錯**：正式環境直接訊息條目中，來源使用者訊息短於 60 字元者 32% 正確，較長者 66% 正確；76 個來源中有 66 個是討論串回覆。

解讀（推論）：短的討論串回覆（例如「好，這次用 X」）多半是一次性指示，脫離前文後容易被誤判為規則；但量測顯示補上前文並沒有讓抽取更準，所以更有效的處理方式可能是在閘門或抽取時對短訊息採更嚴格的標準，而不是補上下文。這一點尚未量測。

## 6. 限制與未解問題

- 外部量測大多衡量召回（答對過去問題），不是寫入精確率；唯一直接量測寫入品質影響的 arXiv 2505.16067 是任務 agent 的經驗記憶。將其結論套到 mikan 屬推論。
- mikan 的兩個評審一致度只有 52–74%，絕對精確率會因評審而異；做決策時應看同一評審下的相對排名，並保留人工抽查。
- 「短訊息更嚴格」、「quote 子字串檢查」、「delete op」都尚未在 mikan 量測，需依 AGENTS.md 先建驗收評估。
- 抽取模型改為可獨立設定屬於新設定（設計變更），依 AGENTS.md 需先列出選項與取捨讓使用者決定。
- ChatGPT 與 Cursor Memories 未公開寫入規則或數字；ChatGPT 頁面經 reader proxy 取得。Cursor 現行文件已無 Memories 頁面，是否停用沒有第一方聲明。
- 廠商自報的數字（mem0 v3、Letta 部落格、Zep 論文）彼此矛盾，且常互相質疑對方的設定，本文只當參考。
