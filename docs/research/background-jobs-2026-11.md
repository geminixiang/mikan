# Background jobs instead of task threads (2026-11)

The refactor scope ([refactor-scope-2026-11.md](refactor-scope-2026-11.md)) replaces `start_task`, `task_status`, the Jev task-intent classifier and its canned replies with background shell jobs in the same session. This page records the research (AGENTS.md steps 1–3): the reference designs, what mikan does today, the experiments, and the candidates with their numbers. Installed versions: pi-durable and pi-env 1.5.2.

## Reference designs

|                  | `pi-bg-bash`                                                                                  | Codex `codex-terminal`                                                                                  | pi-mobile `src/jobs/`                                                  |
| ---------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Start            | Separate tool `bash_bg`; the model decides up front                                           | `exec_command` runs every command and promotes it to a `job_id` when it outlives `yield_time_ms` (10 s) | `bash` on a direct computer promotes after 10 s                        |
| Process          | Host `child_process`, `detached: true`, wrapper writes exit code                              | Host pipes, owner-fenced session                                                                        | `set -m; nohup` shell script, job dir per job                          |
| Records          | `~/.pi/bg-bash/jobs.json` and logs                                                            | In memory, paged output with an unread cursor                                                           | `~/.pi-mobile/jobs/<id>/{command,cwd,owner,limit,pid,log,exit,reason}` |
| Output           | `bash_bg_output` tool                                                                         | `write_stdin` polls (stdin writes too)                                                                  | Model reads the log                                                    |
| Kill             | `bash_bg_kill` tool                                                                           | Close the session                                                                                       | Watchdog at the 2 h limit, stop                                        |
| Completion       | Message with exit code and last 30 lines; `followUp` when busy                                | One compact steer naming the job, no output, suppressed when a poll already returned the exit           | Watch trigger wakes the bot                                            |
| Restart          | Survives `/reload` (records on disk)                                                          | Cleaned up on dispose                                                                                   | Records on disk; `lost` when the process is gone without an exit       |
| Fits mikan as is | No: a `pi-coding-agent` extension spawning on the host, not in the sandbox, not on pi-durable | No: host pipes, no restart survival                                                                     | No: `set -m` fails in the sandbox (below)                              |

What carries over: a record directory per job with the exit code written last (pi-mobile, pi-bg-bash), a fixed time limit (pi-mobile; its `lost` state was first planned and then replaced by that limit, see [Simplifications](#simplifications-decided-by-the-owner)), one completion notice that does not repeat what a poll already showed (Codex), the output tail in the notice so the model rarely needs a second call (pi-bg-bash).

## mikan today

`start_task` (Slack top-level messages only) posts an acknowledgement, creates a `background` anchor task and a child conversation owned by it, and runs the brief in a new thread session on the requester's sandbox. `task_status` lists tasks from pi-durable ownership records. In the DM and in task threads, every message is first classified by Jev (`status` / `steer` / `request`); status gets a canned reply without a model turn, steer is submitted with `whenBusy: "steer"`. A finished task writes its answer into the requester's transcript and mentions the user.

Size of the feature: three feature-only files (302 lines), about 500 lines of branches in `slack/bot.ts`, `session-store.ts`, `runner.ts`, `session.ts`, `presenter.ts`, `conversation-runtime.ts`, `types.ts`, `prompt.ts`, and three test files plus the acceptance eval (1,655 lines). The steering chain (`MessagingEventHandler.steer` → `steerRun` → `session.steer` → `mikan.control_input` entry and its history-sync filter) has one production caller, the task-intent path.

ADR 0021 is out of date in four places: tasks are offered for channel top-level messages too, not only DMs; the `taskRoot` office-log entries are gone (tasks are found through pi-durable ownership); its decisions 5–7 were replaced by ADR 0027; and no code kills recorded guest process groups at startup.

## Owner's decision (2026-11-22)

Task threads were removed first, without a replacement ([ADR 0032](../adr/0032-remove-task-threads.md)), because nothing in use called `start_task`. The owner then asked for the background job tool anyway, with [pi-bg-bash](https://github.com/geminixiang/pi-stuff/tree/main/packages/pi-bg-bash) as the reference for its core: start a job and get an ID at once, and when the job exits, post its exit code and the tail of its output to the session and give the agent a turn. Its other features (`notify_on`, `idle_warn`, `wait_until`, `at`, `fail_on`, `preflight`, approval) are not taken: schedules are the `event` tool's, and the rest can follow a measured need. C1 below is that core for a sandboxed office.

**Chosen: C1.** It is the thinnest candidate that tells the agent a job ended. C0's measured failure (no notice, silent idle-stop kill) is what C1 adds; C2 and C3 cost more code or state for the same result.

### C1 shape

- Tool `bash_background { label, command }`, offered on every platform. It starts the wrapper through the session env and returns the job ID and the guest paths of `log`, `exit`, `pid`. Reading output, listing jobs and killing go through the existing `bash`; the tool result names the paths, and the prompt gains one line in its tool list.
- Guest files: `<office dir>/.jobs/<id>/` with `log`, `pid` (the command's group), and `exit` (written last, through a rename). The tool takes `<id>` from `api.memo`, and the start begins with `mkdir`.
- Host record, in the office's state directory (`jobs.json`): job ID, command, label, owning session key with its thread, user and conversation kind, the guest path of the job directory, start time, how it ended, and whether the notice was delivered.
- Watcher: one per process, polls only jobs without a delivered notice, every second. Exit file → notice; 2 h → kill the group and a notice that the job ended without an exit code. Startup reads every office's records before the first idle check, retains containers with running jobs, and, once the platform bots have started, sends the notices that were never delivered.
- Notice: `[job <id> exited <code> after <duration>] <command>` and a second line naming the log, with none of the output (see [The notice carries no output](#the-notice-carries-no-output)), delivered through `MessagingBot.enqueueEvent` as an event that names the owning session (`job:<id>`).

Open choice, delivery to a busy session: queue the notice behind the current turn (chosen), or steer it into the turn. Steering reaches the model sooner, but a steer admitted after the turn answered starts a run mikan does not present (E9); it is reconsidered only with a test showing mikan follows that run.

## Implementation research (2026-11-22)

The owner asked for C1 with three simplifications. This section records them, what a second pass over the code found, the experiments on the final wrapper, and the acceptance eval.

### Simplifications decided by the owner

| Planned in C1                                                                 | Built instead                                                                                         | Consequence                                                                                                                                                                                                        |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Record the container's `StartedAt` and report a job as `lost` when it changes | No container inspection. A job has one fixed limit of 2 hours                                         | A job whose container was stopped or replaced under it is reported when the limit is reached, as "ended without an exit code", not at once. Until then the model sees no exit file and a log that stopped growing. |
| Offer the tool on Slack only, deliver through a Slack continuation            | One neutral seam: `MessagingBot.enqueueEvent` with an event that names its session, on every platform | No Slack-only capability and no optional method on the bot contract.                                                                                                                                               |
| A prompt section naming the job paths                                         | One line in the prompt's tool list; the tool description and the tool result carry the rest           | The system prompt grows by one line.                                                                                                                                                                               |
| Remove a job's directory and record 7 days after its notice                   | Drop the host record after 7 days; leave the directory                                                | Logs stay in the office until the model or a person removes them. The host deletes nothing in a directory the guest can fill with links.                                                                           |

### Delivery on each platform

`MessagingBot.enqueueEvent(event: ConversationEvent)` is implemented by all four adapters and is what scheduled events use. `ConversationEvent` already has `sessionKey`, and the runtime serializes by it (`ConversationRuntime.handleEvent` → `SessionLifecycle.enqueue`, `src/runtime/conversation-runtime.ts`), so an event that names a busy session runs after that session's turn on any platform. What each adapter did with a named session before this change:

| Platform | Before                                                                                                                                                                                                                                                                                                                                                                 | Change                                                                                                                                                                                                                                                                                                                                                                                        |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Slack    | `enqueueEvent` (`src/adapters/slack/bot.ts`) posted an anchor message for every event without `thread_ts` and replaced the event's session with the anchor's thread, so a session without a thread (a DM's top level) could not be named. An event with `thread_ts` ran in that thread, but waited in the conversation's queue first, behind a busy top-level session. | An event with `sessionKey` skips the anchor and is offered to that session's queue, the queue ordinary messages of the session use. Events without `sessionKey` take the old path unchanged. The answer goes to the thread the session key names when the event carries no `thread_ts`: a job started in a scheduled event's anchor thread has a thread session but no thread on its message. |
| Telegram | `withScheduledEventSession` (`src/sessions/session-key.ts`) gives a new session only to an event with neither `sessionKey` nor `thread_ts`; `createTelegramAdapters` derives the session from `event.sessionKey`. A named session already worked.                                                                                                                      | None. A test pins it.                                                                                                                                                                                                                                                                                                                                                                         |
| Discord  | Same session handling as Telegram, but `createDiscordAdapters` (`src/adapters/discord/context.ts`) treated every `ts` that is not a scheduled-event ID as a message to reply to, so an answer to a job notice would have fetched a message named `job:<id>` and failed.                                                                                                | `isDiscordMessageReference` also excludes job notice IDs.                                                                                                                                                                                                                                                                                                                                     |
| GitHub   | One flat session per issue or pull request; `persistentTopLevelSessionKey` uses `event.sessionKey`. A named session already worked.                                                                                                                                                                                                                                    | None. A test pins it.                                                                                                                                                                                                                                                                                                                                                                         |

Where the answer is posted follows from the event's `thread_ts`, which the job record takes from the message that started the job: a Slack or Discord thread, the Telegram message it replied to, or the top level. In a Slack channel whose reply mode is `thread`, a job started from a top-level message is answered at the channel's top level, because there is no message to thread under.

A notice has no triggering message, and the presenter acknowledges the first tool of every run with a reaction (`acknowledgeWorkOnce`, `src/harness/presenter.ts`). On Slack, Telegram and GitHub that would have called the platform's reaction API with `job:<id>` on every notice turn that uses a tool, and logged a warning. The three contexts now offer no reaction for a job notice, as Discord's already did for any synthetic ID. Scheduled events are left as they are: Slack skips them, Telegram and GitHub still try and log the failure. Telegram rejects an ordinary message sent while its session is busy (`busyPolicy: "reject"`); an injected event is not a message and queues.

### Where the watcher lives

`src/events/jobs.ts`, in the scheduling module. That module's responsibility in `ARCHITECTURE.md` is to turn a host-side record into a normal conversation event and submit it through the platform-neutral `MessagingBot` port, loading every registered office's records once at start. The job watcher has exactly that shape, with an exit file in place of a timer. The alternatives:

| Place                    | Why not                                                                                                                                   |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `src/sandbox/`           | The sandbox module knows containers and execution environments, not sessions or bots; delivery would pull the messaging contract into it. |
| `src/runtime/`           | The runtime owns runner lifecycle per session. A watcher there would add office-wide polling and file reading to the run path.            |
| `src/harness/tools/`     | A tool lives for one runner; the watcher must outlive every runner and start before any exists.                                           |
| A new `src/jobs/` module | One file does not justify a module, a README, and an `architecture.toml` record.                                                          |

The tool (`src/harness/tools/bash-background.ts`) receives a `BackgroundJobSink` the same way the `event` tool receives its store; the composition root gives the watcher the provisioner as its `JobContainers` port (`retain`, `exec`), so `src/events/` imports nothing from `src/sandbox/`.

### Experiments on the final wrapper

On the published image, in a container started with `--cap-drop ALL --security-opt no-new-privileges` and a bind-mounted office directory:

| #   | Question                                                                                   | Result                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| --- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| E13 | Does the final start script behave as E5, E6 and E12 found?                                | Yes. The command runs under `bash` in the exec's working directory; `pid`, `log` and `exit` appear on the host; exit code 7 reads as 7. A second start with the same directory exits with the script's own code 97 and starts nothing.                                                                                                                                                                                                                                                                                                                                           |
| E14 | Does `<engine> exec <container> sh -c 'kill -- -"$(cat pid)"'` end a job and its children? | Yes: no process of the job is left, and the wrapper then writes exit 143. So the watcher has to make the job terminal when it reaches the limit, or the late exit file would produce a second notice. A second kill exits 1; on a stopped container `exec` exits 1 without starting it.                                                                                                                                                                                                                                                                                          |
| E15 | What does the host see when the guest replaces `log` or a job directory with a link?       | The link resolves on the host, outside the office: a plain `readFile` of a file under `.jobs/<id>/` would return a host file of the guest's choosing. The watcher therefore pins `.jobs` and `.jobs/<id>` without following links and reads `exit` with `O_NOFOLLOW`, at most 16 bytes. It does not read `log` at all.                                                                                                                                                                                                                                                           |
| E16 | Is `pid` usable as soon as it exists?                                                      | Not with the wrapper of E12, which wrote `$!` right after starting the command: the file existed before the command had called `setsid`, so `kill -- -$(cat pid)` found no such group. The job now writes `$$` itself after `setsid` and then `exec`s the command: 0 of 25 and 0 of 40 missed, every job exited 143, and E13 and E14 give the same results. |

Read from the code, not run: the kill reads the `pid` file inside the container, so the host never parses it; a guest that writes another number there can only signal processes in its own container.

### The notice carries no output

The first build put the last 20 lines of the log (2 KB at most) in the notice, as pi-bg-bash does. The owner removed it on review. A notice is input to the model, not a tool result, so the tail skipped the secret redaction every tool result gets, and it placed text a command printed in front of the model in the starting user's name. Reading the log is one `bash` call, which is redacted. The host now reads a single guest-written file, `exit`, and the link-safe read shrank to "a regular file of at most 16 bytes". The eval's B and C cases now check that the job's output is in the log and not in the notice; the job prints a value its command does not contain, because the first version's check for the tail matched the command's own text in the notice's first line. The cost is one more tool call per finished job, and the earlier rows of this page that mention a tail (the reference table, the candidates table) describe the references and the first plan, not what was built.

### Measured size

The estimate for C1 was about 310 lines. Built: about 480 lines of production code (the watcher and records 276, the tool 128, the bounded link-safe read 23, wiring and the adapter changes the rest) and about 1,000 lines of tests. The difference is the record schema, the restart path, and reading guest files safely, which the estimate did not count.

### Limits found and kept

- A notice that is queued behind a turn and not yet started when mikan stops is lost, as a queued message is. The record is marked delivered when the platform accepts the event, not when its run starts.
- The mark is written right after the platform accepts the event. A crash between the two delivers the notice again after the restart.
- A crash between creating the job directory and starting the wrapper leaves a directory without a job. A replay then reports the job as started, and the model learns otherwise at the limit.
- Without a running container there is nothing to kill at the limit; the job is reported either way.
- A notice is input to the model in the name of the user who started the job, and its turn runs with that user's credentials. Its text is the job's ID, exit code, duration, command, and log path, all from the host record; nothing the job printed is in it.
- The directories are opened without following links, but only Linux then reads through the opened descriptor (`/proc/self/fd`); on macOS `pinDirectoryNoFollow` falls back to the path, so a guest that swaps a directory between the check and the read is not excluded there.
- The time in "after <duration>" comes from the exit file's modification time, which the guest sets; it is clamped between the start and now.

## Accepted regressions

- Multi-step model work can no longer move to another thread. A long agent turn in the DM's top level queues the next message behind it, as any session does; the agent is expected to move the slow command, not the reasoning, into a job. Baseline: `start_task` lets the DM keep chatting during the whole task.
- Status questions are answered by a model turn that reads `.jobs/`, not by a canned reply.
- Steering a running turn from the DM top level goes away with the task-intent path.

## Removal condition (for the ADR)

Check on 2027-02-22 from production tool counts: if `bash_background` has fewer than 20 calls in the previous 30 days, remove the tool and the watcher; the remaining path is the shell's own backgrounding ([ADR 0033](../adr/0033-background-jobs.md)).

## Verification on Slack

A local daemon built from this change, on the `oci` sandbox, was asked in a direct message on a real Slack workspace to run a 20-second command in the background. The tool returned the job ID in 0.7 s and the model answered at once. A second message sent while the job ran was answered right away. When the job exited, the notice arrived in the same session within a second, the model read the log with `bash`, and posted the output. The state directory has to be on a path the container engine shares with the host: with a workspace the engine's VM did not share, the job ran but the host never saw its exit file, which is the "sandbox stopped" case the limit covers.
