# Background jobs instead of task threads (2026-11)

The refactor scope ([refactor-scope-2026-11.md](refactor-scope-2026-11.md)) replaces `start_task`, `task_status`, the Jev task-intent classifier and its canned replies with background shell jobs in the same session. This page records the research (AGENTS.md steps 1–3): the reference designs, what mikan does today, the experiments, and the candidates with their numbers. Installed versions: pi-durable and pi-env 1.5.2.

## Reference designs

|                  | `pi-bg-bash`                                                                                  | Codex `codex-terminal`                                                                                  | pi-mobile `src/jobs/`                                                  |
| ---------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Start            | Separate tool `bash_bg`; the model decides up front                                           | `exec_command` runs every command and promotes it to a `job_id` when it outlives `yield_time_ms` (10 s) | `bash` on a direct computer promotes after 10 s                        |
| Process          | Host `child_process`, `detached: true`, wrapper writes exit code                              | Host pipes, owner-fenced session                                                                        | `set -m; nohup` shell script, job dir per job                          |
| Records          | `~/.pi/bg-bash/jobs.json` and logs                                                            | In memory, paged output with an unread cursor                                                           | `~/.pi-mobile/jobs/<id>/{command,cwd,owner,limit,pid,log,exit,reason}` |
| Output           | `bash_bg_output` tool                                                                         | `write_stdin` polls (stdin writes too)                                                                  | Model reads the log                                                    |
| Kill             | `bash_bg_kill` tool                                                                           | Close the session                                                                                       | Watchdog at the 2 h limit, stop                                        |
| Completion       | Message with exit code and last 30 lines; `followUp` when busy                                | One compact steer naming the job, no output, suppressed when a poll already returned the exit           | Watch trigger wakes the bot                                            |
| Restart          | Survives `/reload` (records on disk)                                                          | Cleaned up on dispose                                                                                   | Records on disk; `lost` when the process is gone without an exit       |
| Fits mikan as is | No: a `pi-coding-agent` extension spawning on the host, not in the sandbox, not on pi-durable | No: host pipes, no restart survival                                                                     | No: `set -m` fails in the sandbox (below)                              |

What carries over: a record directory per job with the exit code written last (pi-mobile, pi-bg-bash), `lost` as a state (pi-mobile), one completion notice that does not repeat what a poll already showed (Codex), the output tail in the notice so the model rarely needs a second call (pi-bg-bash).

## mikan today

`start_task` (Slack top-level messages only) posts an acknowledgement, creates a `background` anchor task and a child conversation owned by it, and runs the brief in a new thread session on the requester's sandbox. `task_status` lists tasks from pi-durable ownership records. In the DM and in task threads, every message is first classified by Jev (`status` / `steer` / `request`); status gets a canned reply without a model turn, steer is submitted with `whenBusy: "steer"`. A finished task writes its answer into the requester's transcript and mentions the user.

Size of the feature: three feature-only files (302 lines), about 500 lines of branches in `slack/bot.ts`, `session-store.ts`, `runner.ts`, `session.ts`, `presenter.ts`, `conversation-runtime.ts`, `types.ts`, `prompt.ts`, and three test files plus the acceptance eval (1,655 lines). The steering chain (`MessagingEventHandler.steer` → `steerRun` → `session.steer` → `mikan.control_input` entry and its history-sync filter) has one production caller, the task-intent path.

ADR 0021 is out of date in four places: tasks are offered for channel top-level messages too, not only DMs; the `taskRoot` office-log entries are gone (tasks are found through pi-durable ownership); its decisions 5–7 were replaced by ADR 0027; and no code kills recorded guest process groups at startup.

## Facts and experiments

Each experiment ran outside `src/` (`.workspace/bg-jobs-probe/`, ignored by git) against a throwaway container, through pi-env's public `Connection` and `RemoteExecutionEnv`. The container came from an old local build of the sandbox image that has no `bash`, so every command ran under `sh`; the experiments are repeated on the current published image before implementation.

Idle stop: the provisioner stops a managed container 10 minutes after its last env operation (`provisioner.stopIdle`, checked every 10 minutes and once at startup with `lastUsed` seeded from the container's `StartedAt`). `markUsed` runs at the start of each env operation only, so a job with no other sandbox activity is killed by the idle stop (E4). `retain()` exists and is used by the desktop.

Same-session delivery: only Slack can queue a run into an existing session (`continueInterruptedRuns` → `enqueueContinuation`). Scheduled events open a new anchor thread on Slack and use other paths on Discord, Telegram and GitHub.

## Cases mikan has that the references do not

| Case                                                           | Consequence                                                                                                                                                                                                      |
| -------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One container per office, shared by every session in it        | A job records its owning session on the host; the notice goes to that session. The guest can write the office directory, so routing never reads a guest file.                                                    |
| Job ends while mikan is down                                   | The host record marks a notice as delivered; startup sends exactly one notice for every ended job that has none.                                                                                                 |
| Records accumulate                                             | A job's directory and record are removed 7 days after its notice; the model can copy a log it wants to keep.                                                                                                     |
| Idle stop                                                      | While a job runs, its container is retained; the retain is rebuilt from the records at startup, before the first idle check.                                                                                     |
| A retain with no bound pins a container forever (a dev server) | Jobs get a fixed limit (2 h, as in pi-mobile); at the limit the job is killed and reported `timed_out`.                                                                                                          |
| Daemon restart, mikan restart, container re-provisioned        | Jobs started with `setsid` keep running (E2, E3); logs and exit codes live in the office directory, so a re-provisioned container still has them, and the recorded `StartedAt` decides `lost` (E7).              |
| The model kills a job with `bash`                              | The command runs in its own group under the wrapper, so the wrapper writes the exit code (E12).                                                                                                                  |
| Tool call replayed after a restart                             | The job ID is taken from a tool memo and the start is guarded by `mkdir` (E6).                                                                                                                                   |
| The owning session when the job ends                           | Slack queues a run in the owning session, as continuation does; a busy session runs it after the current turn. Other platforms have no such path yet, so the tool is offered on Slack only, as `start_task` was. |
| `stop`                                                         | Stops the run only; jobs are background by intent and keep running. The model or user kills them with `kill -- -<pgid>`.                                                                                         |
| `/new`                                                         | Jobs keep running; the notice lands in the new context of the same session key.                                                                                                                                  |

| Against the bar                                | Fails the core idea's "tools the task needs": the model cannot learn that a job ended | Delivers information (log path, exit code, tail) and leaves reading, polling and killing to the model's existing `bash`                               | Not built on the foundation: replaces Pi's bash                                                              | Built on pi-durable, but stores a commit per check and still needs the scan |

**Chosen: C1.** It is the thinnest candidate that tells the agent a job ended. C0's measured failure (no notice, silent idle-stop kill) is what C1 adds; C2 and C3 cost more code or state for the same result.

### C1 shape

- Tool `bash_background { label, command }`, offered on Slack when the sandbox is `oci` (the consolidation decided oci-only). It starts the wrapper through the session env and returns the job ID and the guest paths of `log`, `exit`, `pid`. Reading output, listing jobs and killing go through the existing `bash`; the prompt names the paths.
- Guest files: `<office dir>/.jobs/<id>/` with `log`, `pid` (the command's group), and `exit` (written last, through a rename). The tool takes `<id>` from `api.memo`, and the start begins with `mkdir`.
- Host record, in the office's state directory: job ID, command, owning session key, start time, the container's `StartedAt`, and whether the notice was delivered.
- Watcher: one per process, polls only running jobs (250 ms–1 s). Exit file → notice; container stopped, or running with another `StartedAt` → `lost`; 2 h → kill the group and `timed_out`. Startup reads every office's records before the first idle check, retains containers with running jobs, and sends the notices that were never delivered.
- Notice: `[job <id> exited <code> after <duration>] <command>` plus the last 20 lines (bounded to 2 KB) and the log path, delivered as a queued Slack run in the owning session (`job:<id>`).

Open choice, delivery to a busy session: queue the notice behind the current turn (chosen), or steer it into the turn. Steering reaches the model sooner, but a steer admitted after the turn answered starts a run mikan does not present (E9); it is reconsidered only with a test showing mikan follows that run.

## Removed with this change

`src/harness/tools/task.ts`, `src/adapters/slack/task-intent.ts`, `src/adapters/slack/task-status.ts`; their branches in `slack/bot.ts` (task context functions, `enqueueTaskRun`, `isTaskControl`, `deliverTaskUpdate`), `session-store.ts` (anchor, `openTask`, `createTaskSession`, `reportTaskOutcome`, `listTasks`, `isTask`, `readExecution`, `inspectExecution`), `runner.ts` (`allowTask*`, `initialTask`, `steerRun`), `session.ts` (tool filter, batch block), `presenter.ts` (task tool special cases, completion mention), `prompt.ts` (Slack Tasks), `types.ts` (`TaskStatus`, responder task functions, `steer`), the `task_intent` Jev caller, and the tests and eval for them. Kept: `jev-context.ts` (auto-reply uses it), `detachOnShutdown` (continuation uses it). `TaskAnchors` is unregistered too: E8 shows existing databases still open.

Production use of `start_task` is not in the counts the refactor review used; reading it needs production access, which the owner grants.

Existing task threads after the upgrade: a reply goes through normal thread intake into the same child conversation (the session index still maps the thread), and a finished run no longer reports to the requester.

## Accepted regressions

- Multi-step model work can no longer move to another thread. A long agent turn in the DM's top level queues the next message behind it, as any session does; the agent is expected to move the slow command, not the reasoning, into a job. Baseline: `start_task` lets the DM keep chatting during the whole task.
- Status questions are answered by a model turn that reads `.jobs/`, not by a canned reply.
- Steering a running turn from the DM top level goes away with the task-intent path.

## Removal condition (for the ADR)

Check on 2027-02-11 from production tool counts: if `bash_background` has fewer than 20 calls in the previous 30 days, remove it; the remaining path is the prompt-taught `setsid` command (C0).
