# Slack platform APIs mikan does not use yet (2026-10)

Question: which Slack app APIs, beyond the ones mikan calls today, would help mikan or the people who talk to it, and which of them work on Slack's free plan?

Sources are Slack's developer docs read on 2026-10-09 (each page is also served as Markdown at `<url>.md`; `https://docs.slack.dev/llms.txt` indexes them), and a POC run the same day on a free workspace with a Socket Mode app declared as an agent (`agent_view`, `assistant:write`). The POC scripts are in `.workspace/slack-apis/`. Statements about mikan come from `src/adapters/slack/` and `deploy/examples/slack-*-manifest.json` at `main`.

| Situation                         | What the user sees                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DM message with a threaded reply  | The DM's main view lists the user's messages, each with "1 reply"; the answer lives in the thread. Setting `processing` on the thread opened it in the side pane automatically in the DM, not in a channel                                                                                                                                                                                                                                                                                                                                                                         |

Without a title the root message text is the title. `suspended` shows a clock icon; `closed` stays in the list. The context menu offers only "Open in split view", "Copy link", and "Close conversation"                                                                                                                                                                                                                                                                        |
| Existing traffic                  | The test workspace already listed 44 sessions, created by the compatibility bridge from mikan's `assistant.threads.setStatus`/`setTitle` calls in DM and channel threads                                                                                                                                                                                                                                                                                                                                                                                                           |
| Channel thread                    | Works with `recipient_user_id`; the session is listed for the root author (`initiator_user_id`), so sessions under a bot-authored root did not appear in the user's list                                                                                                                                                                                                                                                                                                                                                                                                           |
| Processing                        | "Stop mikan" with a spinner under the reply; the indicator stays until the app sets another status or one hour passes                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Thread without a status call      | `chat.postMessage` and `chat.update` in a thread, without `agents.sessions.setStatus`, created no session and no sidebar entry                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| User renames                      | "Edit thread name" in the thread header opens a dialog ("all participants can see it"); saving delivered `agent_session_title_changed` with `title`, `previous_title`, `user`, `channel`, and `thread_ts`                                                                                                                                                                                                                                                                                                                                                                          |
| User closes                       | "Close conversation" removes the session from that user's list without any event to the app; a later bot reply, a new `processing` status, and a reply from the user in that thread did not bring it back                                                                                                                                                                                                                                                                                                                                                                          |
| Mobile                            | The user checked the mobile app by eye and found it similar to desktop; not measured                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| mikan today (1.2.2, `agent_view`) | A DM reply is posted top-level with `chat.postMessage` and updated with `chat.update`, while the status ("Thinking", then empty) goes through `assistant.threads.setStatus` on the user's message. Slack opens that message's thread in the side pane with "mikan is working" and a spinner, and the thread stays empty because the answer appears in the main view; the main view also shows "mikan is working" under the user's message. No native stop button appeared on this bridged status, and tool progress shows as a "• step" line in the reply that turns into "✓ step" |

The friction comes from a model mismatch. Slack treats each thread as one session and each new top-level DM message as a new session; mikan keys a durable session to a DM's top-level conversation, and a channel thread gets its own session key. Under `agent_view` the DM therefore reads as a list of questions with the answers hidden in threads, and the sidebar fills with one entry per question.

## The five-minute stream limit in mikan (reproduced)

mikan streams natively only when it replies inside an existing thread (`response-lifecycle.ts`: `replyInThread && rootTs`); top-level channel and DM replies use `chat.postMessage` plus `chat.update` and are unaffected. Four runs on a local daemon at 1.2.2:

| Run                                                                      | Path                   | Result                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------------------------------ | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One `sleep 330` tool call, top-level @mention in a channel               | Buffered `chat.update` | Finished after 5.6 minutes with the right answer                                                                                                                                                                                                                                                          |
| Four 100-second rounds with a text update after each, top-level @mention | Buffered `chat.update` | Finished after 8.9 minutes; every update succeeded                                                                                                                                                                                                                                                        |
| Four rounds, @mention inside a thread                                    | Native stream          | The first tool's progress line changed from "•" to "✓" at 1 min 40 s, which is not an append, so mikan stopped the stream and switched to `chat.update` before the limit                                                                                                                                  |
| One `sleep 330` tool call, @mention inside a thread                      | Native stream          | The stream expired while the tool ran. At the end `chat.stopStream` returned `message_not_in_streaming_state`, mikan logged "Slack replaceResponse error", and the progressive renderer fell back to `chat.update`, which succeeded on the expired stream message, so the user saw the right final answer |

What the user loses is limited to the stream's own behavior; what the operator gets is noise. The failing `stopStream` goes through `reportResponseError`, which reports a `chat_platform` error with severity `error` to Sentry, so every threaded run whose first streamed text stays append-only for more than about five minutes produces one error event although the reply is correct. A POC confirmed that `chat.update` works on an expired stream message, which is why the fallback recovers. Not measured: whether the working indicator from the bridged `assistant.threads.setStatus` also disappears when the stream expires mid-run, and how often production hits this path beyond what Sentry records. Production Sentry held one grouped issue for `message_not_in_streaming_state` over 90 days: 4 events from 2 users, dated 2026-08-18, 09-02, 09-08, and 09-22, with operation `replace_response` three times and `set_working` once, one of them in a DM; none since.

## What changes for mikan

| Area                     | Today                                                       | Free-plan target                                                                                                                                      | Why                                                                                                                                                                                                                                       |
| ------------------------ | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Session status and title | `assistant.threads.setStatus`/`setTitle` through the bridge | `agents.sessions.setStatus`/`rename`, explicit `active` at run end                                                                                    | The bridge goes away with `assistant_view` in February 2027; sessions add `suspended` for "waiting on you" and `closed`                                                                                                                   |
| Stop                     | mikan's own "Force Stop" button and `stop`                  | Subscribe to `agent_session_stopped` and route it to the existing force-stop path                                                                     | Native button in every processing thread; Slack does not stop the run for the app                                                                                                                                                         |
| Tool progress            | Text lines such as "✓ jev · label"                          | `task_update` chunks in a plan, with tool output and links as task `output` and `sources`                                                             | Native, collapsible progress; only inside threads, and a stream must use chunks throughout; a stream lives about 5 minutes and holds about 12,000 characters, so long runs roll over to a new streamed message, and a plan keeps 50 tasks |
| Long replies             | `msg_too_long` handling in `response-lifecycle.ts`          | Keep; the measured stream cap is about 12,000 characters per message                                                                                  | Confirms the existing guard is needed for streams too                                                                                                                                                                                     |
| Feedback                 | none                                                        | `feedback_buttons` under each final reply, recorded per run                                                                                           | The accept/dismiss signal the proactive-work design needs                                                                                                                                                                                 |
| Viewed context           | `assistant_view`-shaped `context.channel_id`, logged only   | Read `context.entities` from `app_context_changed` and `message.im`, and tell the model which channel, thread, or canvas the user has open            | "Summarize this" from split view can then resolve "this"                                                                                                                                                                                  |
| Rich output              | `slack_blockkit` tool, GFM tables to `table` blocks         | Teach `slack_blockkit` the new blocks (`data_table`, `data_visualization`, `card`, `carousel`, `container`)                                           | Charts and paged tables for reports; `alert` stays out                                                                                                                                                                                    |
| Search                   | none                                                        | Optional `search_slack` tool using the triggering event's `action_token`                                                                              | Keyword search over public channels on free plans; scopes should be optional                                                                                                                                                              |
| Canvas                   | none                                                        | One channel or DM canvas per conversation as a living document the bot owns: create when absent, edit sections by ID, read with `canvases.getContent` | Works on the free plan when the bot is a channel member; write mentions in canvas syntax and keep a fallback for `restricted_action`                                                                                                      |

## Constraints found on the way

- **History rate limit for unlisted commercial apps**: since 2025-05-29, new installs of apps distributed commercially outside the Marketplace get `conversations.history` and `conversations.replies` at 1 request per minute and 15 objects per request. Internal, customer-built apps keep the old limits. A self-hosted mikan is an internal app, so boot backfill is unaffected. ([changelog 2025-05-29, 2025-06-03](https://docs.slack.dev/changelog/))
- **Notifications**: desktop notifications read text from blocks first; mobile reads only `text`. mikan already sends a plain-text fallback. ([changelog 2026-07-13](https://docs.slack.dev/changelog/))
- **Optional scopes**: `bot_optional` in the manifest lets an installer skip sensitive scopes such as `search:read.*`, which Slack's governance guide recommends. ([changelog 2026-03-16](https://docs.slack.dev/changelog/), [governance](https://docs.slack.dev/ai/agent-governance))

## Not worth adopting

| API                                                         | Reason                                                                                                                  |
| ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `chat.scheduleMessage`                                      | mikan's event scheduler already covers it; Slack caps it at 120 days and drops scheduled messages that carry `metadata` |
| `reminders.*`                                               | User-token only (`reminders:write`); Slack degraded these APIs when it replaced reminders with "Save it for later"      |
| Slack MCP server (`is_mcp_enabled`) and Slackbot MCP client | They let other AI clients reach Slack or let Slackbot call tools; mikan is already a bot with its own tools             |
| Lists API                                                   | Lists need a paid plan (measured: `unknown_method`)                                                                     |
