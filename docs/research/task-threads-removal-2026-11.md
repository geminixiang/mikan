# Removing task threads (2026-11)

Question: can mikan remove Slack task threads (`start_task`, `task_status`, the Jev task-intent classifier with its canned replies, and the steering chain behind them) without adding a replacement in the same change?

[background-jobs-2026-11.md](background-jobs-2026-11.md) planned this removal together with a `bash_background` tool. The two are split: this change only removes, and the background-jobs design is decided on its own later. Sources: the code paths below, ADRs [0021](../adr/0021-tasks-as-background-child-conversations.md) and [0027](../adr/0027-interrupted-runs-continue-after-restart.md), a production deployment's tool counts, and the acceptance eval in `.workspace/task-threads-removal-eval/`.

## Why remove it now

- In a deployment in use, the model hardly used the feature: `start_task` went uncalled over the period reviewed, and `task_status` was called rarely. The people using mikan will barely notice the removal.
- The feature is three files of its own, branches in a dozen more, and the largest Slack test file. A thread reply pays for it: a read of the office storage decides whether it is a task control message before it is acknowledged.
- It makes relevance decisions for the model: Jev classifies a message as status, steer, or request, and a status question gets a canned reply the model never sees.

## What existed

`start_task` (top-level Slack messages, DMs and channels) posted an acknowledgement, created a `background` anchor task and a child conversation owned by it, and ran the brief in a new thread session. `task_status` listed those children from pi-durable ownership records. Every DM message that was a task-thread reply, arrived while a task ran, or matched a status-question pattern went through Jev first: `status` got a canned reply without a model turn, `steer` was submitted into the running turn with `whenBusy: "steer"`, and `request` fell through to a normal turn. A finished run in a task thread mentioned the requester and wrote its answer into the requester's transcript.

## What an existing installation holds

A session database written before this change can contain: terminal and pending `mikan.task-anchor` tasks, child conversations owned by them and indexed under their thread's session key, `start_task` and `task_status` calls in transcripts, `[background task … finished]` user entries in requester transcripts, and `mikan.control_input` custom entries. Experiment E8 of the background-jobs research showed that such a database opens with `TaskAnchors` unregistered; the upgrade case below repeats that through the Slack bot, including a task that was still running when the old process stopped.

## Accepted regressions

- Multi-step work can no longer move to another thread. A long turn at the top level of a DM or channel queues the next message behind it, as any session does. Before, the conversation kept answering while the task ran.
- A status question is an ordinary message: the model answers it, after the running turn when one is going. Before, it got a canned reply at once without a model call.
- Steering a running turn goes away, from the DM top level and from inside a task thread. A message sent while a turn runs is answered after it.
- A finished run in an existing task thread no longer mentions the requester and no longer writes its answer into the requester's transcript.

## Acceptance eval

`.workspace/task-threads-removal-eval/task-threads.eval.ts` drives `SlackMessagingBot` and the conversation runtime with a fake socket, a fake Web API, Pi's faux provider, and Jev mocked as not configured. One scripted model serves both checkouts: it reads the tools it is offered and calls `start_task` only when it is there. The baseline is commit `ab60e0e0`; the upgrade rows read state that the baseline wrote, including one finished task (steered once) and one task still running when the process stopped.

Baseline and expected results were recorded before the implementation. The after column is the run on the changed tree, with the upgrade state written by the baseline; the raw results are `baseline.json` and `after.json` beside the eval. Every row matched.

## Verification on Slack

A local daemon built from this change answered a direct message on a real Slack workspace that asked for a 15-second command: it ran in the direct message itself and the output came back there. A second message sent while it ran was not answered until the first finished, then got its own answer. The Slack E2E workflow covers stop, threads, queueing, and scheduled events.
