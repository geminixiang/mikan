この監査は [コアインターフェース](/core-interfaces/) の境界を用います。目標はファイル数を最小化することではありません。core を小さな安定した契約の集合として説明可能にし、任意のポリシーをその背後に移すことです。

## 目標とする core

最小限で一貫した mikan の core は次のとおりです:

1. 1 つの正規化された conversation input と 1 つの response port；
2. session を直列化し runner lifecycle を所有する 1 つの runtime；
3. 1 つの model turn のための 1 つの harness インターフェース；
4. 意図的に分離された 1 つの session store と 1 つの platform log store；
5. すべての tool I/O のための 1 つの executor インターフェース；
6. 1 つの credential-resolution の seam；
7. 任意の platform、command、tool、extension、sandbox の機能のための registries。

| ------ | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |

| P0     | `MessagingBot` に変更理由が多すぎる                             | lifecycle、output、upload/reaction、private diagnostics、event queue、metadata が 1 つのインターフェースになっている                  | 正規化された platform port を任意の機能から分離し、それらを合成する 1 つの adapter オブジェクトを保つ                          |

## 簡素化してはならないもの

一見の重複の中には、重要なセマンティクスを守るものがあります:

- `log.jsonl` を agent session JSONL から分離して保つ。これらは異なる真実を記録し、リカバリを支える。
- host paths を runtime paths から分離して保つ。これらを統合すると container/remote 実行が壊れ、host-only のデータを露出し得る。
- model-provider credentials を sandbox vault credentials から分離して保つ。
- per-session queues を保つ。グローバルな直列化は並行性を無駄にし、直列化なしは conversation の順序を破壊する。
- platform trust policy を明示的に保つ。platform 名から credential の安全性を推測するのは危険。
- executor が所有する file transport を保つ。これを shell snippets に置き換えると、quoting、サイズ、partial-write の失敗が再び入り込む。
- extension code を host-only に、sandbox workspace data を分離して保つ。

## 提案するインターフェース

### 1 つの正規化された input

```ts
interface ConversationInput {
  platform: MessagingInfo;
  conversation: {
    id: string;
    kind: ConversationKind;
    vaultId?: string;
  };
  message: {
    id: string;
    parentId?: string;
    sessionKey?: string;
    actor: { id: string; name?: string };
    text: string;
    attachments: readonly Attachment[];
  };
  respond: ConversationResponder;
}
```

runtime は、古い call sites のためだけに `ConversationEvent` と `ConversationMessage` を導出します。adapters と tests が envelope を使うようになったら、両方の互換形を削除します。

### 合成された platform capabilities

```ts
interface PlatformPort {
  readonly info: MessagingInfo;
  lifecycle: { start(): Promise<void>; stop(): Promise<void> };
  messages: PlatformMessages;
  capabilities?: {
    reactions?: PlatformReactions;
    uploads?: PlatformUploads;
    privateMessages?: PlatformPrivateMessages;
  };
}
```

これにより、任意のメソッド名による feature detection がなくなり、commands/extensions が必要とする正確な機能を要求できるようになります。

### 明示的な runtime 依存

```ts
interface ConversationRuntimeOptions {
  workingDir: string;
  sandbox: SandboxConfig;
  createRunner: RunnerFactory;
  commands?: readonly CommandDefinition[];
  vault?: VaultResolver;
  resources?: SandboxResourceController;
  portals?: PortalServices;
  platformCapabilities?: PlatformCapabilities;
  platformToolPacks?: readonly PlatformToolPackFactory[];
}
```

runtime は、別のサブシステムの service bag からコンストラクタの形を継承すべきではありません。

### 正直な sandbox registry

```ts
interface SandboxRegistry {
  register<T extends SandboxConfig>(adapter: SandboxAdapter<T>): void;
  parse(value: string): SandboxConfig;
  validate(config: SandboxConfig): Promise<void>;
  createExecutor(config: SandboxConfig, context: ExecutorContext): Promise<Executor>;
}
```

## 移行シーケンス

### Phase 1 — パッケージ境界を強制する

1. `.`、`./extension`、`./runtime` のためのパッケージ `exports` map を追加する。
2. root の `export *` を明示的なリストに置き換える。
3. 生成された宣言またはチェック済みのシンボルリストを用いて、API-extractor 風のスナップショットテストを追加する。
4. 現在 export されているがサポートされないシンボルを、削除前に 1 リリースの間 deprecated としてマークする。

これを最初に行うのは、consumers が偶発的な exports に依存した後では、あらゆる内部リファクタリングが難しくなるためです。

### Phase 2 — platform input を統一する

1. `ConversationInput` と、それから現在の runtime 呼び出しへの adapter を追加する。
2. 1 つの platform adapter とそのテストを一度に 1 つずつ変換する。
3. `handleEvent(event, bot, context)` を `handle(input)` に変更する。
4. すべての platforms が移行した後、重複フィールドと互換 adapter を削除する。

これにより、`ts` と `message.id`、`thread_ts` と `threadTs`、event の `user` と message の `userId` をめぐる一貫性のバグが取り除かれるはずです。

### Phase 3 — capabilities を合成する

1. `MessagingBot` から message、reaction、upload、private-message の各 port を抽出する。
2. 既存の bots を、その SDK コードを変えずに適応させる。
3. bot 全体ではなく、狭い capabilities を commands、extensions、events、admin に渡す。
4. 独立した呼び出し側が残っていなければ `ChatAdapter` を廃止する。

### Phase 4 — runtime 構築と commands を簡素化する

1. `Omit<CommandServices, ...>` の継承を、明示的な runtime options に置き換える。
2. portal services を、3 つの token-store フィールドと 1 つの URL ではなく、1 つの任意オブジェクトにする。
3. command メタデータと handler 登録を `CommandDefinition` に統合する。
4. platform 登録、parsing インベントリ、handler 順序を、その definition リストから生成する。

### Phase 5 — 任意の execution 製品を分離する

1. 既存の default 関数を wrapper として保ちつつ `SandboxRegistry` を導入する。
2. host/container/image を default の distribution として登録する。

### Phase 6 — composition root を縮小する

`main.ts` は、CLI 設定をパースし、registries/services をインスタンス化し、選択された製品を起動し、shutdown を調整すべきです。Platform SDK の初期化と backend 固有のポリシーは、それぞれのモジュールに残すべきです。有用な完了基準は、composition root がビジネスロジックではなく設定のように読めることです。

## 受け入れ基準

簡素化が完了するのは、次のときです:

- 新しい platform が、1 つの正規化された input adapter と宣言された output capabilities を実装する；
- 新しい sandbox が、core の switch や配列を編集せずに 1 つの adapter を登録する；
- runtime 構築が、個々の portal token-store 型に言及しない；
- command の追加が、複数の platform インベントリではなく、1 つの definition と 1 つの handler 実装を変更する；
- root の npm 宣言面が、ドキュメント化されたシンボルのみを含む；
- 永続化された session/event/config 形式と trust/path の不変条件が、互換のまま保たれる；
- 各 phase の後で、既存のユニットテスト、build、lint、`knip` がパスする。

## 推奨される最初の pull request

最初の実装 PR は挙動中立に保ちます:

1. 互換 subpaths を持つパッケージ `exports` map を追加する；
2. 重複する root 型 re-exports を明示的な exports に置き換える；
3. public API のスナップショットテストを追加する；
4. `ConversationInput` と変換ヘルパーを導入するが、移行するのは 1 つの adapter だけにする；
5. 機能を削除せずに deprecation を記録する。

これを、sandbox backend の削除や永続化形式の変更と組み合わせないでください。それらの変更は、rollback と運用上のリスクが異なります。
