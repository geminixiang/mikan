## 前提条件

- Node.js `>=24.15.0`
- 少なくとも 1 組の完全な Slack、Telegram、Discord、または GitHub credentials
- PM2 ユーザーの永続的な `~/.mikan`（mikan の state を置く場所）。working directory の既定値は `~/.mikan/workspace`
- `image:*` または `container:*` 使用時に PM2 user が利用できるコンテナエンジン：Docker（既定）、Podman、nerdctl。`CONTAINER_ENGINE` で選択します（[Image sandbox](/ja/sandbox/image/#コンテナエンジン) を参照）

公開されている `mikan-sandbox` image は tool runtime であり、standalone mikan server image ではありません。PM2 は host 上で `mikan` を実行し、image mode は host Docker daemon を通じて containers を作成、管理します。

## PM2 デプロイ

<Steps>

1. mikan と PM2 をインストールします：

   ```bash
   npm i -g @geminixiang/mikan pm2
   ```

2. PM2 が実行するユーザーで setup を実行します。chat platform の tokens、LLM provider、sandbox
   image を尋ね、`~/.mikan/settings.json`、secrets file `~/.mikan/mikan.env`（mode `0600`）、
   PM2 の設定 file `~/.mikan/ecosystem.config.cjs` を書き込みます：

   ```bash
   mikan onboard
   ```

   secrets はすべて `~/.mikan/mikan.env` に置かれ、ecosystem file が起動時に読み込みます。secrets を
   ecosystem file や PM2 自身の環境に置かないでください。後から platform や変数を追加するときは
   この file を編集します。`mikan env` はすべての変数と現在の設定状況を表示します。既存の
   `~/.mikan/ecosystem.config.cjs` はそのまま残ります。

3. 選んだ sandbox image を pull します。onboard がこの行を表示します。公開 image は約 900 MB です：

   ```bash
   docker pull ghcr.io/geminixiang/mikan-sandbox:latest
   ```

4. process を起動し、永続化します：

   ```bash
   pm2 start ~/.mikan/ecosystem.config.cjs
   pm2 save
   pm2 startup
   ```

5. `pm2 startup` が出力したコマンドを実行し、boot 時の自動起動を有効にします。

</Steps>

ecosystem file は supervision 専用です：process 名、restart policy、graceful-shutdown timeout、
`mikan.env` の loader、そして `args` の sandbox mode（flag の一覧は `mikan --help` を実行して
ください）。挙動（model、sandbox limits、reply modes）は `~/.mikan/settings.json` に残ります。
working-directory 引数は任意です。指定しない場合、mikan は `~/.mikan/workspace` を使用し、
初回起動時に作成します。

相対 workspace paths は PM2 の current working directory から解決されます。絶対 paths を使うと、service の移行や reboot 後に別の workspace を暗黙に開くことを防げます。

## アップグレード

```bash
npm i -g @geminixiang/mikan
pm2 reload mikan
```

新しいバージョンに未適用の [State マイグレーション](#state-マイグレーション) がある場合は、reload の前に実行してください。

`~/.mikan/mikan.env` を編集した後は、環境が再読み込みされるように ecosystem file 経由で reload
します：

```bash
pm2 reload ~/.mikan/ecosystem.config.cjs
```

<Aside type="note" title="Graceful reload">
  同梱の PM2 設定は停止シグナル後、SIGKILL まで最大 6 分待機します。mikan は新しいメッセージの
  受付を即座に止め、実行中の runs を最大 5 分完了させ、残りを中止してその会話に再起動の通知を
  投稿し、observability exporters の flush と shutdown を最大 5 秒待ちます。fork モードの `pm2
  reload` は旧プロセス終了後に 新プロセスを起動するため、drain
  中はどのプロセスもプラットフォームに接続していません。 オフピークにデプロイしてください。
</Aside>

### State マイグレーション

永続化ファイルの形式を変えるリリースには、番号付きのマイグレーションが含まれます。未適用のマイグレーションがある間、daemon は起動を拒否し、実行すべき `mikan migrate` コマンドをそのまま表示します。daemon が自分でファイルを変換することはありません。適用済みのマイグレーションは `~/.mikan/migrations.json` に記録されます。

新しいバージョンをインストールしたら、未適用のマイグレーションを確認します。`--dry-run` は読み取りだけなので、daemon の実行中でも安全です。daemon と同じ `--sandbox` と workspace を指定します:

```bash
mikan migrate --sandbox=image:mikan-sandbox:latest --dry-run
```

`No pending migrations.` と表示されたら、上の手順で reload します。そうでなければ daemon を停止し、適用してから再起動します:

```bash
pm2 stop mikan
mikan migrate --sandbox=image:mikan-sandbox:latest
pm2 start mikan
```

安全に判断できない場合、マイグレーションは記録されずに停止します。たとえば、名前が複数の有効なプラットフォームに当てはまる directory（Telegram と Discord を両方動かしているときの数字だけの id）や、同じ会話が古い名前と新しい名前の両方に存在する場合です。エラーには各パスと対処方法が表示されます。曖昧な所有者は `--owner <conversationId>=<platform>`（繰り返し指定可）で指定して再実行してください。すでに成功したマイグレーションは適用済みのまま残ります。

### 0.5.3 からのアップグレード

1.0.0 は 0.5.3 のインストールをその場でマイグレーションします。サポートされるアップグレードはこれだけで、1.0.0 のプレリリースにしか存在しなかった形式は変換されません。マイグレーションが済むまで 1.0 の daemon は起動せず、そのインストール用の `mikan migrate` コマンドを表示します。

1. **バックアップする。** 0.5.3 の daemon を止め、state directory と working directory の両方をコピーします。マイグレーションは両方の directory を rename します。
2. **1.0 をインストールする。** Node.js 24.15.0 以降が必要です: `npm i -g @geminixiang/mikan@latest`。
3. **state を `~/.mikan` に移す。** 1.0 には `--state-dir` がありません。0.5.3 が state を別の場所に置いていた場合は、その directory を `~/.mikan` に移動し、process manager が実行するコマンドから `--state-dir` を外してください。
4. **サポートされる sandbox を選ぶ。** 1.0 が動かすのは `host`、`container:<name>`、`image:<image>` です。`firecracker:*` や `cloudflare:*` を使っていた 0.5.3 のインストールは、先にこのいずれかへ切り替えてください。
5. **provider key を移す。** 0.5.3 が `~/.pi/mikan/auth.json` から読んでいた key は移行されません。`~/.mikan/mikan.env` に設定するか、`models.json` に置いてください。
6. **マイグレーションする。** 0.5.3 の working directory と、daemon が今後使う sandbox を渡し、プレビューしてから適用します:

   ```bash
   mikan migrate --workspace /srv/mikan --sandbox=image:mikan-sandbox:latest --dry-run
   mikan migrate --workspace /srv/mikan --sandbox=image:mikan-sandbox:latest
   ```

7. **起動してログを確認する。** daemon は各 `settings.json` について `Settings that mikan ignores; remove them from <path>` を記録し、1.0 が読まなくなった `llm.autoReply` などの 0.5.3 の設定を挙げます。読まなくなった環境変数についても、代わりの設定とともに `Environment variable that mikan ignores` を記録します。それらを削除し、`sentry.dsn` の設定は `SENTRY_DSN` に移してください。

`mikan migrate` は次を行います:

- conversation directory とその vault を、生の conversation id から office key へ rename する
- `host` の per-user vault と `container:*` の vault を、hash された identity key へ rename する
- 各会話の `settings.json` を `~/.mikan/conversations/<office-key>/` へ移動する
- 各会話の session file をその `sessions.db` に取り込み、元のファイルを `~/.mikan/conversations/<office-key>/sessions-v3/` に残す
- `<workspace>/events/*.json` を各会話の host 専用 event store へ移動する
- 0.5.3 の sandbox container を削除する。次のメッセージで現在のイメージから空の `/root` で再作成される
- mikan に `~/.mikan/models.json` がまだなければ、`~/.pi/agent/models.json`（または `$PI_CODING_AGENT_DIR/models.json`）をコピーする
- 各 conversation directory から `last_prompt.jsonl` と `auto-reply.disabled` を削除する（1.0 はどちらも書き込まない）

アップグレード後に利用者が気づく変化:

- スラッシュなしで使えるのは `session` と `stop` だけです。`new`、`model`、`auto-reply` は `/pi-new` のようなスラッシュ形式が必要です。
- Auto-reply は Slack 専用で、`on`、`off`、`jev` を受け付けます。auto-reply のルールを設定していたチャンネルは、すべてのトップレベルメッセージに返信するようになります。`/pi-auto-reply off` または `jev` で絞り込んでください。
- sandbox 内では、会話のファイルは `/workspace/<office-key>` にあります。以前の session で agent が引用したパスは、古い `/workspace/<conversation-id>` を指したままです。
- extension は読み込まれなくなりました。`skills/` directory の skill は引き続き読み込まれます。

[changelog](https://github.com/geminixiang/mikan/blob/main/CHANGELOG.md) には、embedder 向けのパッケージインターフェースの縮小を含め、0.5.3 以降のすべての変更が載っています。

## Health endpoint

portal server は `LINK_PORT` が設定されている場合、または `LINK_URL` によって既定 port `8181` が使われる場合にのみ存在します：

```bash
curl http://127.0.0.1:8181/health
# {"ok":true}
```

`/health` は HTTP process の liveness check にすぎません。platform connections、Docker、sandbox provisioning、LLM providers、event delivery は検証しないため、唯一の readiness signal として使用しないでください。

mode 固有の要件は [GitHub で保守されている PM2 ecosystem file](https://github.com/geminixiang/mikan/blob/main/deploy/pm2/ecosystem.config.cjs) と [Sandbox modes](/ja/sandbox/) を参照してください。
