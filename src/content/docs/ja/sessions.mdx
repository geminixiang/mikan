## プラットフォームセッションモデル

session key は `conversationId` 単体か、scoped session の場合は `conversationId:suffix` です。suffix は、そのプラットフォームが thread や reply の対象を識別するために使う値です。

| プラットフォーム | `sessionKey` ルール                                                                                                 | 備考                                                                                      |
| ---------------- | ------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| Slack            | top-level と DM: `channelId`; thread（DM 内も含む）: `channelId:threadTs`                                           | thread sessions は直近のチャット履歴から bootstrap される固定ファイルです                 |
| Discord          | DM と shared top-level: `channelId`; thread: `parentChannelId:threadChannelId`; reply: `channelId:repliedMessageId` | guild thread は parent channel と thread 自身の id の組で指し示されます                   |
| Telegram         | private chat: `chatId`; shared top-level: `chatId:messageId`; shared reply: `chatId:repliedMessageId`               | ネイティブ thread model はないため、返信先のメッセージが scope になります                 |
| GitHub           | `GH_<owner>_<repo>_<number>`                                                                                        | 1 つの issue または pull request が 1 つのフラットな session。inline review thread も含む |

## Session key と office

session key は生のプラットフォーム値のままです。`src/sessions/session-key.ts` の文法が office key を目にすることはありません。runtime state は、その conversation の office と session key の組で指し示されるため、生の conversation id を共有する 2 つのプラットフォームが互いの runner、queue、stop state を選ぶことは決してありません。ストレージの path は office に従い、session ファイルは sandbox から見えない `~/.mikan/conversations/<officeKey>/sessions/` 配下に置かれます。

## セッション識別子の安全性

session key は常にちょうど 1 つの会話に属します。プラットフォームアダプターは scoped key を提供できますが、会話の intake と runtime は、その会話 prefix が受信中の会話と異なる key を拒否します。会話の識別子と scoped suffix は、session storage に影響を与える前に、path separators、制御文字、特殊な `.` / `..` セグメントも拒否します。Thread session files は既存の名前と永続化の挙動を保持します。加えて sessions module は、symlink の session target を拒否し、導出された paths がその office の sessions ディレクトリ内に留まることを保証します。session header に記録された path は開かれず、親 session は session id で探します。

## Session の始まり方

各 office はすべての session を 1 つの pi-durable SQLite storage に保存します。top-level session と、thread または reply の範囲ごとに 1 つの session です。

Thread は、それを生んだものから始まります。各 run は自分を開始したメッセージを記録し、log は run の回答とともにそのメッセージと実行した session を記録します。ある run の回答の下、またはその run を開始したメッセージの下に開かれた thread は、その run を fork します。その session の run 終了時点までの context（tool call とその出力を含む）を持って始まるので、agent はコマンドを再実行せずに出力を答えられます。それ以外の thread は、起点のメッセージと自分の返信だけで始まります。この動作より前からある thread は、元の context を保ちます。

Session 自身の回答がその記憶です。チャット同期は、他の人や他の bot のメッセージ、mikan の通知を、発言者を明示したチャット行として追加します。別の session の run が投稿した回答は、その session に任せます。より古い履歴は `log.jsonl` で検索でき、agent は `history` tool で同じ conversation のすべての session とチャットログを、tool call とその出力を含めて検索できます。

## 運用者向けの移行

`mikan migrate` は 0.5.3 の session file を office の `sessions.db` に取り込み、元の `sessions/` ディレクトリを `sessions-v3/` に移します。詳しくは [State マイグレーション](/ja/deployment/#state-マイグレーション) を参照してください。

## Clean session とメモリ

Top-level session は長期間使い続けられ、Pi の自動 compaction が model context を上限内に保ちます。`/new` は直ちに session をリセットします。model は空の context から始まり、以前のエントリは storage に残って `history` tool と session view から読めます。前の会話の要約や memory 処理の待機は行いません。既存の conversation `MEMORY.md` は独立して利用できます。

**Memory capture** は、知識が述べられた時点で記録します。人が起点の run が終わるたびに、mikan は Jev にユーザーが永続的な知識（継続的なルール、納品の好み、システムやワークフローに関する永続的な事実、訂正など）を確立したかを判定させます。確立していれば、会話のモデルが conversation `MEMORY.md` の `## Captured knowledge` に個別の行を追加または更新し、取得日と元メッセージを付記します。スケジュールされた event の run は対象外で、workspace 共有メモリには書き込みません。key のある [Jev provider](/ja/configuration/#jev) がない場合は無効です。取得した行の訂正や削除は、他のメモリと同じく agent に依頼してください。

conversation `MEMORY.md`（**Memory anchor**）は、run 中に agent が、run の終了後に Memory capture が書き込みます。スケジュールによる書き換えや整理はありません。これは簡潔で修正可能な案内情報であり、最終的な真実ではありません。より新しい conversation evidence が優先されます。変更可能な外部状態は、その回答の実行中に Live source または現在の API から確認する必要があります。利用できない場合、mikan は memory を現在の真実として扱わず、確認できないことを伝えます。

<Aside type="tip" title="監査可能な記録を保持">
  Private chat で `new` / `/new` を使うと直ちに新しく始められます。手動で削除しない限り、以前の
  session files は確認用にディスク上へ残ります。
</Aside>
