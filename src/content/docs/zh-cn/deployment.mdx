## 前提条件

- Node.js `>=24.15.0`
- 至少一套完整的 Slack、Telegram、Discord 或 GitHub 凭证
- PM2 用户持久存在的 `~/.mikan`，mikan 的状态都存放在这里；工作目录默认为 `~/.mikan/workspace`
- 使用 `image:*` 或 `container:*` 时，PM2 用户可以使用 Docker

发布的 `mikan-sandbox` 镜像是工具运行时，不是独立的 mikan 服务器镜像。PM2 在主机上运行 `mikan`；image 模式通过主机 Docker daemon 创建和管理容器。

## PM2 部署

<Steps>

1. 安装 mikan 和 PM2：

   ```bash
   npm i -g @geminixiang/mikan pm2
   ```

2. 以 PM2 运行时的用户身份执行设置。它会询问聊天平台的 token、LLM provider 和沙箱镜像，
   然后写入 `~/.mikan/settings.json`、secrets 文件 `~/.mikan/mikan.env`（权限 `0600`）以及 PM2
   配置文件 `~/.mikan/ecosystem.config.cjs`：

   ```bash
   mikan onboard
   ```

   所有 secret 都存放在 `~/.mikan/mikan.env`，ecosystem 文件会在启动时加载它；切勿把 secret 放进
   ecosystem 文件或 PM2 自身的环境。之后要添加平台或变量时，直接编辑这个文件；`mikan env` 会列出
   所有变量及当前的设置状态。已存在的 `~/.mikan/ecosystem.config.cjs` 会保持不变。

3. 拉取你选择的沙箱镜像。onboard 会打印这一行；官方镜像约 900 MB：

   ```bash
   docker pull ghcr.io/geminixiang/mikan-sandbox:latest
   ```

4. 启动并持久保存进程：

   ```bash
   pm2 start ~/.mikan/ecosystem.config.cjs
   pm2 save
   pm2 startup
   ```

5. 运行 `pm2 startup` 输出的命令，启用开机启动。

</Steps>

ecosystem 文件仅用于进程监管：进程名称、重启策略、优雅关闭超时、`mikan.env` 加载器，以及
`args` 中的沙箱模式（运行 `mikan --help` 查看参数参考）。行为（模型、沙箱限制、回复模式）仍保留在
`~/.mikan/settings.json` 中。工作目录参数是可选的；不提供时 mikan 会使用 `~/.mikan/workspace`
并在首次启动时创建它。

相对工作区路径从 PM2 的当前工作目录解析。绝对路径可避免服务迁移或重启后无意中打开其他工作区。

## 升级

```bash
npm i -g @geminixiang/mikan
pm2 reload mikan
```

如果新版本有待应用的 [State 迁移](#state-迁移)，请先执行再重新加载。

编辑 `~/.mikan/mikan.env` 之后，请通过 ecosystem 文件重新加载，以便重新读取环境：

```bash
pm2 reload ~/.mikan/ecosystem.config.cjs
```

<Aside type="note" title="优雅重新加载">
  随附的 PM2 配置会在 SIGTERM 后等待最多 60 秒，再发送 SIGKILL。mikan 会先排空对话运行，停止 events
  watcher，并给 observability exporters
  最多五秒钟完成刷新和关闭。超过进程管理器超时时间的运行仍可能被终止。
</Aside>

### State 迁移

会改变持久化文件格式的版本会附带一个有编号的迁移。只要还有待应用的迁移，daemon 就会拒绝启动，并打印应执行的完整 `mikan migrate` 命令；它不会自行转换任何文件。已应用的迁移记录在 `~/.mikan/migrations.json`。

安装新版本后，先检查有没有待应用的迁移。`--dry-run` 只读取，daemon 运行时也可以安全使用。请传入与 daemon 相同的 `--sandbox` 和工作区：

```bash
mikan migrate --sandbox=image:mikan-sandbox:latest --dry-run
```

如果输出 `No pending migrations.`，按上面的方式重新加载即可。否则先停止 daemon、应用迁移，再重新启动：

```bash
pm2 stop mikan
mikan migrate --sandbox=image:mikan-sandbox:latest
pm2 start mikan
```

遇到无法安全判断的情况，迁移会停止且不会被记录，例如：目录名同时符合多个已启用平台（Telegram 与 Discord 同时运行时的纯数字 id），或同一对话同时存在新旧两个名称。错误信息会列出每个路径及处理方法。用 `--owner <conversationId>=<platform>`（可重复）指定有歧义目录的所有者后再运行一次；已经成功的迁移会保持已应用。

### 从 0.5.3 升级

1.0.0 会直接在原地迁移 0.5.3 的安装。这是唯一支持的升级路径：仅在 1.0.0 预览版中出现过的格式不会被转换。迁移完成之前，1.0 的 daemon 不会启动，并会打印适用于你的安装的 `mikan migrate` 命令。

1. **备份。** 停止 0.5.3 的 daemon，复制它的 state directory 和 working directory。迁移会重命名两边的目录。
2. **安装 1.0。** 需要 Node.js 24.15.0 及以上：`npm i -g @geminixiang/mikan@latest`。
3. **把状态移到 `~/.mikan`。** 1.0 没有 `--state-dir`；如果 0.5.3 的状态放在其他位置，请把该目录移到 `~/.mikan`，并从进程管理器执行的命令中去掉 `--state-dir`。
4. **选择支持的沙盒。** 1.0 支持 `host`、`container:<name>` 和 `image:<image>`。使用 `firecracker:*` 或 `cloudflare:*` 的 0.5.3 安装，要先改用其中一种。
5. **迁移 provider key。** 0.5.3 从 `~/.pi/mikan/auth.json` 读取的 key 不会被迁移；请设置到 `~/.mikan/mikan.env`，或保留在 `models.json`。
6. **迁移。** 传入 0.5.3 的 working directory 和 daemon 之后要用的沙盒，先预览再执行：

   ```bash
   mikan migrate --workspace /srv/mikan --sandbox=image:mikan-sandbox:latest --dry-run
   mikan migrate --workspace /srv/mikan --sandbox=image:mikan-sandbox:latest
   ```

7. **启动并检查日志。** daemon 会针对每个 `settings.json` 记录 `Settings that mikan ignores; remove them from <path>`，列出 1.0 不再读取的 0.5.3 设置，例如 `llm.autoReply`；也会针对每个不再读取的环境变量记录 `Environment variable that mikan ignores`，并说明该改用什么。请把它们删除；`sentry.dsn` 设置要改成 `SENTRY_DSN` 环境变量。

`mikan migrate` 会：

- 把对话目录及其 vault 从原始对话 id 重命名为 office key；
- 把 `host` 模式的每用户 vault 和 `container:*` 的 vault 重命名为哈希后的 identity key；
- 把每个对话的 `settings.json` 移到 `~/.mikan/conversations/<office-key>/`；
- 把每个对话的会话文件导入它的 `sessions.db`，原文件保留在 `~/.mikan/conversations/<office-key>/sessions-v3/`；
- 把 `<workspace>/events/*.json` 移到各对话仅主机可见的事件存储；
- 删除 0.5.3 的沙盒容器；下一条消息到来时会用当前镜像重建，`/root` 从空开始；
- 如果 mikan 还没有 `~/.mikan/models.json`，就复制 `~/.pi/agent/models.json`（或 `$PI_CODING_AGENT_DIR/models.json`）；
- 删除每个对话目录里的 `last_prompt.jsonl` 和 `auto-reply.disabled`，1.0 不会再写这两个文件。

升级后用户会注意到的变化：

- 只有 `session` 和 `stop` 可以不加斜杠；`new`、`model`、`auto-reply` 需要使用斜杠形式，例如 `/pi-new`。
- Auto-reply 只支持 Slack，接受 `on`、`off` 或 `jev`。原本设有 auto-reply 规则的频道，现在会回复每一条顶层消息；可以用 `/pi-auto-reply off` 或 `jev` 缩小范围。
- 在沙盒里，对话的文件位于 `/workspace/<office-key>`。agent 在旧会话里引用的路径，仍指向旧的 `/workspace/<conversation-id>`。
- 不再加载 extension；`skills/` 目录里的 skill 仍会加载。

[changelog](https://github.com/geminixiang/mikan/blob/main/CHANGELOG.md) 列出自 0.5.3 以来的所有变更，包括面向嵌入者的包接口缩减。

## 健康端点

Portal 服务器仅在设置 `LINK_PORT` 时存在；如果 `LINK_URL` 使默认端口 `8181` 生效，也会存在：

```bash
curl http://127.0.0.1:8181/health
# {"ok":true}
```

`/health` 仅检查 HTTP 进程是否存活。它不会验证平台连接、Docker、沙箱 provision、LLM 提供商或事件投递，因此不要将其用作唯一的就绪信号。

请参阅 [GitHub 上维护的 PM2 ecosystem 文件](https://github.com/geminixiang/mikan/blob/main/deploy/pm2/ecosystem.config.cjs)和[沙箱模式](/zh-cn/sandbox/)了解特定模式的要求。
