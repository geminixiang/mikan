## 平台会话模型

会话密钥要么是单独的 `conversationId`，要么是限定范围会话的 `conversationId:suffix`。后缀就是平台用来标识话题或回复目标的那个值。

| 平台     | `sessionKey` 规则                                                                                       | 说明                                                          |
| -------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| Slack    | 顶层和 DM：`channelId`；话题（包括 DM 中的）：`channelId:threadTs`                                      | 话题会话是根据近期聊天历史记录初始化的固定文件                |
| Discord  | DM 和共享顶层：`channelId`；话题：`parentChannelId:threadChannelId`；回复：`channelId:repliedMessageId` | guild 话题以其父频道加上话题自身的 id 来寻址                  |
| Telegram | 私聊：`chatId`；共享顶层：`chatId:messageId`；共享回复：`chatId:repliedMessageId`                       | 没有原生话题模型，因此被回复的那条消息就是范围                |
| GitHub   | `GH_<owner>_<repo>_<number>`                                                                            | 一个 issue 或 pull request 是一个扁平会话，含内联 review 话题 |

## 会话密钥与办公室

会话密钥保持为原始平台值——`src/sessions/session-key.ts` 中的语法从不接触 office key。运行时状态按该对话的办公室加其会话密钥寻址，因此两个共用同一原始对话 id 的平台永远无法选中彼此的 runner、队列或 stop 状态。存储路径则跟随办公室：会话文件位于沙箱看不到的 `~/.mikan/conversations/<officeKey>/sessions/` 下。

## 会话身份安全

一个会话密钥始终只属于一个对话。平台适配器可以提供带范围的密钥，但对话接收层和运行时会拒绝其对话前缀与传入对话不符的密钥。对话身份和范围后缀也会在影响会话存储之前拒绝路径分隔符、控制字符以及特殊的 `.` / `..` 段。话题会话文件保留其现有名称和持久化行为；会话模块另外会拒绝符号链接会话目标，并确保派生路径始终位于该办公室的 sessions 目录内。会话头中记录的路径从不被打开；父会话一律按会话 id 查找。

## 会话如何开始

每个 office 把所有会话存放在一个 pi-durable SQLite 存储中：顶层会话，以及每个话题或回复范围各一个会话。

话题从引起它的事情开始。每次 run 会记录触发它的消息，log 也会在 run 的回答旁记录那条消息和执行它的会话。开在某次 run 的回答下、或开在触发那次 run 的消息下的话题，会 fork 那次 run：它带着该会话到那次 run 结束为止的上下文，包括工具调用及其输出，所以 agent 不必重跑命令就能说出命令输出了什么。其他话题只带起点消息和自己的回复。在此行为之前已存在的话题保留原有上下文。

会话自己的回答才是它的记忆。聊天同步会把其他人、其他 bot 的消息以及 mikan 的通知，以标明发言者的聊天记录加入；其他会话的 run 发出的回答则留给那个会话。更早的历史仍可在 `log.jsonl` 中查询，agent 也能用 `history` 工具搜索同一对话的所有会话与聊天记录，包括工具调用及其输出。

## 运维迁移

`mikan migrate` 会把 0.5.3 的会话文件导入该 office 的 `sessions.db`，并把原来的 `sessions/` 目录移到 `sessions-v3/`；详见 [State 迁移](/zh-cn/deployment/#state-迁移)。

## Clean session 与记忆

顶层会话会长期沿用，Pi 的自动 compaction 会让模型上下文保持在上限内。`/new` 会立即重置会话：模型从空的上下文开始，之前的记录仍留在存储中，`history` 工具与 session view 都能读取。它不会总结前一段对话，也不会等待记忆处理；现有对话 `MEMORY.md` 仍可独立使用。

**Memory capture** 会在知识被说出的当下就记录。每次由真人触发的 run 结束后，mikan 会请 Jev 判断用户是否建立了长期知识，例如长期规则、交付偏好、关于系统或流程的持久事实，或是一项更正。若是，对话所用的模型会在对话 `MEMORY.md` 的 `## Captured knowledge` 下新增或更新单独条目，并标注捕获日期与来源消息。计划 event 的 run 会被跳过，从不写入 workspace 共享记忆；没有任何 [Jev provider](/zh-cn/configuration/#jev) 有 key 时此功能停用。要更正或删除捕获的条目，和其他记忆一样请 agent 修改即可。

对话 `MEMORY.md`（**Memory anchor**）由 agent 在 run 中写入，以及由 Memory capture 在 run 结束后写入；没有任何计划任务会重写或整理它。它是精简且可修订的导向信息，不是最终真相。较新的对话 evidence 优先。可变的外部状态必须在回答当次从 Live source 或当前 API 验证；如果来源不可用，mikan 应说明目前无法验证，而不是把 memory 当作当前真相。

<Aside type="tip" title="保留审计记录">
  在私聊中使用 `new` / `/new`
  可立即重新开始。除非手动删除，否则之前的会话文件仍会保留在磁盘上供检查。
</Aside>
