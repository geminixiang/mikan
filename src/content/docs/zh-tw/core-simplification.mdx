title: 核心簡化

---

本次審視採用[核心介面](/zh-tw/core-interfaces/)中的邊界。目標不是把檔案數量降到最少；而是讓核心能以一小組穩定契約解釋清楚，並把選用政策移到它們之後。

## 目標核心

最小且一致的 mikan 核心是：

1. 一個對話身分，以及一個把它轉成路徑的地方；
2. 一個正規化的對話輸入與一個 response port；
3. 一個序列化 session 並擁有 runner lifecycle 的 runtime；
4. 一個負責 model turn 的 harness 介面；
5. 一個 session store 與一個平台 log store，刻意分開；
6. 一個供所有工具 I/O 使用的 executor 介面；
7. 一個憑證解析 seam；
8. 供選用的 platform、command、tool 與 sandbox 能力使用的 registry。

## 不應被簡化掉的東西

有些看似重複的地方其實保護著重要語意：

- 讓 `log.jsonl` 與 agent session JSONL 分開。它們記錄不同的真實，並支援復原。
- 讓 office key 與原始平台 id 分開。用 raw id 命名目錄或 vault，會讓兩個共用同一個 id 的平台碰到彼此的資料；registry 之所以存在，正是因為這個 key 無法反推。
- 讓 session key 維持原始值。它們是平台值，而把它們與一個 office 配對，正是讓非全域唯一的 key 得以安全的原因——把它們改寫成以 office 為範圍的字串，只會把這道檢查從 runtime 推給每一個呼叫端。
- 讓 host path 與 runtime path 分開。合併它們會破壞 container/remote 執行，並可能暴露僅限 host 的資料。
- 讓 model-provider 憑證與 sandbox vault 憑證分開。
- 保留 per-session queue。全域序列化會浪費並行；不序列化則會破壞對話順序。
- 讓平台信任政策保持明確。從平台名稱推斷憑證安全性是不安全的。
- 保留由 executor 擁有的檔案傳輸。用 shell 片段取代它會重新引入 quoting、size 與 partial-write 的失敗。

## 提議的介面

### 一個正規化輸入

```ts
interface ConversationInput {
  platform: MessagingInfo;
  conversation: {
    address: OfficeAddress;
    kind: ConversationKind;
    vaultId?: string;
  };
  message: {
    id: string;
    parentId?: string;
    sessionKey?: string;
    actor: { id: string; name?: string };
    text: string;
    attachments: readonly Attachment[];
  };
  respond: ConversationResponder;
}
```

runtime 只為舊呼叫端衍生 `ConversationEvent` 與 `ConversationMessage`。一旦 adapter 與測試都使用此 envelope，就刪除這兩種相容形狀。

### 組合式的平台能力

```ts
interface PlatformPort {
  readonly info: MessagingInfo;
  lifecycle: { start(): Promise<void>; stop(): Promise<void> };
  messages: PlatformMessages;
  capabilities?: {
    reactions?: PlatformReactions;
    uploads?: PlatformUploads;
    privateMessages?: PlatformPrivateMessages;
  };
}
```

這移除了依任意方法名稱做的 feature detection，並讓 command 得以請求它們確切需要的能力。

### 明確的 runtime 相依

```ts
interface ConversationRuntimeOptions {
  workspace: Workspace;
  sandbox: SandboxConfig;
  createRunner: RunnerFactory;
  commands?: readonly CommandDefinition[];
  vault?: VaultResolver;
  resources?: SandboxResourceController;
  portals?: PortalServices;
  platformCapabilities?: PlatformCapabilities;
  platformToolPacks?: readonly PlatformToolPackFactory[];
}
```

runtime 不應從另一個子系統的 service bag 繼承其 constructor 形狀。

### 誠實的 sandbox registry

```ts
interface SandboxRegistry {
  register<T extends SandboxConfig>(adapter: SandboxAdapter<T>): void;
  parse(value: string): SandboxConfig;
  validate(config: SandboxConfig): Promise<void>;
  createExecutor(config: SandboxConfig, context: ExecutorContext): Promise<Executor>;
}
```

## Migration 順序

### Phase 1 — 強制執行套件邊界（已完成）

1. `package.json` 宣告 root 與相容的 `./harness`、`./sandbox` entry point。
2. root entry point 使用明確 export 清單，不再 wildcard export harness。
3. `src/test/public-api.test.ts` snapshot runtime export 與 emit declaration，意外變更會讓 CI 失敗。

其餘 phase 現在可在不意外擴大 package interface 的情況下重構內部。

### Phase 2 — 統一平台輸入

1. 加入 `ConversationInput`，以及從它到目前 runtime 呼叫的 adapter。
2. 一次轉換一個平台 adapter 及其測試。
3. 把 `handleEvent(event, bot, context)` 改為 `handle(input)`。
4. 在所有平台都遷移後，刪除重複欄位與相容 adapter。

這應能消除環繞 `ts` 對 `message.id`、`thread_ts` 對 `threadTs`、以及 event `user` 對 message `userId` 的一致性 bug。

### Phase 3 — 組合能力

1. 從 `MessagingBot` 抽出 message、reaction、upload 與 private-message port。
2. 在不改動 SDK 程式碼的情況下調整既有 bot。
3. 把窄化的能力傳給 command、event 與 admin，而非整個 bot。
4. 退役已無使用者的淺層 `ChatAdapter` 介面。（已完成）

### Phase 4 — 簡化 runtime 建構與指令

1. 以明確的 runtime option 取代 `Omit<CommandServices, ...>` 繼承。
2. 讓 portal service 成為一個選用物件，而非三個 token-store 欄位加一個 URL。
3. 把指令 metadata 與 handler 註冊併入 `CommandDefinition`。
4. 從該 definition 清單產生平台註冊、parsing 清單與 handler 順序。

### Phase 5 — 分離選用的執行產品

1. 引入 `SandboxRegistry`，同時保留既有預設函式作為 wrapper。
2. 把 host/container/image 註冊為預設 distribution。

### Phase 6 — 縮小 composition root

`main.ts` 應解析 CLI 設定、實例化 registry/service、啟動所選產品，並協調 shutdown。平台 SDK 初始化與 backend 專屬政策應留在各自模組中。一個有用的完成準則是：composition root 讀起來像設定，而非商業邏輯。

## 驗收準則

當滿足以下條件時，簡化即完成：

- 新增平台時，只需實作一個正規化輸入 adapter 加上宣告的輸出能力；
- 新增 sandbox 時，只需註冊一個 adapter，不需編輯核心 switch 或陣列；
- runtime 建構不再提及個別的 portal token-store 型別；
- 新增指令時，只改動一個 definition 與一個 handler 實作，而非數個平台清單；
- root 的 npm 宣告表面只包含有文件記載的符號；
- 持久化的 session/event/config 格式與 trust/path 不變式保持相容；
- 每個 phase 之後，既有的單元測試、build、lint 與 `knip` 都通過。

## 建議的下一個 pull request

Package boundary 已完成。下一個實作 PR 應保持行為中立：

1. 引入 `ConversationInput` 與轉換 helper，但只遷移一個 adapter；
2. 記錄 deprecation，但不刪除功能。

不要把這個 PR 與移除某個 sandbox backend 或變更持久化格式合併。那些變更有不同的 rollback 與營運風險。
