## 先決條件

- Node.js `>=24.15.0`
- 至少一組完整的 Slack、Telegram、Discord 或 GitHub 憑證
- PM2 使用者持久存在的 `~/.mikan`，mikan 的狀態都放在這裡；working directory 預設為 `~/.mikan/workspace`
- 使用 `image:*` 或 `container:*` 時，PM2 使用者必須可使用 Docker

發布的 `mikan-sandbox` image 是工具 runtime，不是可獨立運作的 mikan server image。PM2 在 host 上執行 `mikan`；image 模式透過 host Docker daemon 建立並管理 containers。

## PM2 部署

<Steps>

1. 安裝 mikan 與 PM2：

   ```bash
   npm i -g @geminixiang/mikan pm2
   ```

2. 以 PM2 執行時的使用者身分執行設定。它會詢問聊天平台的 token、LLM provider 與 sandbox 模式，
   接著寫入 `~/.mikan/settings.json` 與 secrets 檔案 `~/.mikan/mikan.env`（mode `0600`）：

   ```bash
   mikan onboard
   ```

   所有 secret 都放在 `~/.mikan/mikan.env`，ecosystem file 會在啟動時載入它；絕不要把 secret 放進
   ecosystem file 或 PM2 自己的環境。之後要加平台或變數時，直接編輯這個檔案；`mikan env` 會列出所有
   變數與目前已設定的項目。

3. 拉取受管理 sandbox image：

   ```bash
   docker pull ghcr.io/geminixiang/mikan-sandbox:latest
   ```

   選擇 `image:*` 模式時，不要另外啟動長期運作的 container。只有 `container:<name>`
   模式才需要預先存在的 container。

4. 下載 ecosystem file：

   ```bash
   curl -O https://raw.githubusercontent.com/geminixiang/mikan/main/deploy/pm2/ecosystem.config.cjs
   ```

   這個 ecosystem file 只負責 supervision：process 名稱、restart policy、graceful-shutdown
   timeout，以及 `mikan.env` loader。行為（model、sandbox 限制、reply mode）仍留在
   `~/.mikan/settings.json`。

5. 在 `args` 設定 sandbox 模式（執行 `mikan --help` 查看旗標參考）：

   ```js
   args: "--sandbox=image:ghcr.io/geminixiang/mikan-sandbox:latest",
   ```

   working-directory 引數是選用的；若省略，mikan 會使用 `~/.mikan/workspace`，並在首次啟動
   時建立它。

6. 啟動並保存程序：

   ```bash
   pm2 start ecosystem.config.cjs
   pm2 save
   pm2 startup
   ```

7. 執行 `pm2 startup` 印出的指令，啟用開機自動啟動。

</Steps>

相對 workspace 路徑會從 PM2 的 current working directory 解析。使用絕對路徑可避免服務移轉或重開機後，無聲地開啟另一個 workspace。

## 升級

```bash
npm i -g @geminixiang/mikan
pm2 reload mikan
```

如果新版本有待套用的 [State 遷移](#state-遷移)，請先執行再重新載入。

編輯 `~/.mikan/mikan.env` 之後，請透過 ecosystem file 重新載入，讓環境重新讀取：

```bash
pm2 reload ecosystem.config.cjs
```

<Aside type="note" title="Graceful reload">
  隨附的 PM2 設定會在停止訊號後等待最多六分鐘才送出 SIGKILL。mikan 會立即停止接收新訊息，
  讓進行中的執行最多再跑五分鐘，之後中止剩餘的執行並在那些對話張貼重啟通知，最後給 observability
  exporters 最多五秒完成 flush 與 shutdown。fork 模式下的 `pm2 reload`
  是先停舊、再起新，排空期間沒有任何 process 連著平台；請在離峰時段部署。
</Aside>

### State 遷移

會改變持久化檔案格式的版本，會附帶一個有編號的遷移。只要還有待套用的遷移，daemon 就會拒絕啟動，並印出應該執行的 `mikan migrate` 完整指令；它不會自行轉換任何檔案。已套用的遷移記錄在 `~/.mikan/migrations.json`。

安裝新版本後，先檢查有沒有待套用的遷移。`--dry-run` 只會讀取，daemon 執行中也可以安全使用。請帶入與 daemon 相同的 `--sandbox` 與 workspace：

```bash
mikan migrate --sandbox=image:mikan-sandbox:latest --dry-run
```

如果印出 `No pending migrations.`，照上面的方式重新載入即可。否則先停止 daemon、套用遷移，再重新啟動：

```bash
pm2 stop mikan
mikan migrate --sandbox=image:mikan-sandbox:latest
pm2 start mikan
```

遇到無法安全判斷的情況，遷移會停下來且不會被記錄，例如：目錄名稱同時符合多個已啟用平台（Telegram 與 Discord 同時執行時的純數字 id），或同一個對話同時存在新舊兩個名稱。錯誤訊息會列出每個路徑與處理方式。用 `--owner <conversationId>=<platform>`（可重複）指定有歧義目錄的擁有者後再執行一次；已經成功的遷移會維持已套用。

### 從 0.5.3 升級

1.0.0 會直接在原地遷移 0.5.3 的安裝。這是唯一支援的升級路徑：只在 1.0.0 預覽版出現過的格式不會被轉換。遷移完成之前，1.0 的 daemon 不會啟動，並會印出適用於你的安裝的 `mikan migrate` 指令。

1. **備份。** 停止 0.5.3 的 daemon，複製它的 state directory 與 working directory。遷移會改名兩邊的目錄。
2. **安裝 1.0。** 需要 Node.js 24.15.0 以上：`npm i -g @geminixiang/mikan@latest`。
3. **把狀態搬到 `~/.mikan`。** 1.0 沒有 `--state-dir`；如果 0.5.3 的狀態放在其他位置，請把該目錄搬到 `~/.mikan`，並從 process manager 執行的指令中拿掉 `--state-dir`。
4. **選擇支援的沙盒。** 1.0 支援 `host`、`container:<name>` 與 `image:<image>`。使用 `firecracker:*` 或 `cloudflare:*` 的 0.5.3 安裝，要先改用其中一種。
5. **搬移 provider key。** 0.5.3 從 `~/.pi/mikan/auth.json` 讀取的 key 不會被遷移；請設定到 `~/.mikan/mikan.env`，或保留在 `models.json`。
6. **遷移。** 傳入 0.5.3 的 working directory 與 daemon 之後要用的沙盒，先預覽再套用：

   ```bash
   mikan migrate --workspace /srv/mikan --sandbox=image:mikan-sandbox:latest --dry-run
   mikan migrate --workspace /srv/mikan --sandbox=image:mikan-sandbox:latest
   ```

7. **啟動並檢查 log。** daemon 會針對每個 `settings.json` 記錄 `Settings that mikan ignores; remove them from <path>`，列出 1.0 不再讀取的 0.5.3 設定，例如 `llm.autoReply`。請把它們刪掉。

`mikan migrate` 會：

- 把對話目錄及其 vault 從原始 conversation id 改名為 office key；
- 把 `host` 模式的每位使用者 vault 與 `container:*` 的 vault 改名為雜湊後的 identity key；
- 把每個對話的 `settings.json` 移到 `~/.mikan/conversations/<office-key>/`；
- 把每個對話的 session 檔匯入它的 `sessions.db`，原檔保留在 `~/.mikan/conversations/<office-key>/sessions-v3/`；
- 把 `<workspace>/events/*.json` 移到各對話僅 host 可見的事件儲存區；
- 移除 0.5.3 的沙盒容器；下一則訊息進來時會以目前映像重建，`/root` 從空的開始；
- 如果 mikan 還沒有 `~/.mikan/models.json`，就複製 `~/.pi/agent/models.json`（或 `$PI_CODING_AGENT_DIR/models.json`）；
- 刪除每個對話目錄裡的 `last_prompt.jsonl` 與 `auto-reply.disabled`，1.0 不會再寫這兩個檔案。

升級後使用者會注意到的變化：

- 只有 `session` 與 `stop` 可以不加斜線；`new`、`model`、`auto-reply` 要用斜線形式，例如 `/pi-new`。
- Auto-reply 只支援 Slack，接受 `on`、`off` 或 `jev`。原本設有 auto-reply 規則的頻道，現在會回覆每一則頂層訊息；可以用 `/pi-auto-reply off` 或 `jev` 縮小範圍。
- 在沙盒裡，對話的檔案位於 `/workspace/<office-key>`。agent 在舊 session 裡引用的路徑，仍指向舊的 `/workspace/<conversation-id>`。
- 不再載入 extension；`skills/` 目錄裡的 skill 仍會載入。

[changelog](https://github.com/geminixiang/mikan/blob/main/CHANGELOG.md) 列出自 0.5.3 以來的所有變更，包括給 embedder 的套件介面縮減。

## Health endpoint

只有設定 `LINK_PORT`，或 `LINK_URL` 使系統使用預設 port `8181` 時，portal server 才會存在：

```bash
curl http://127.0.0.1:8181/health
# {"ok":true}
```

`/health` 只檢查 HTTP process 是否存活。它不會驗證平台連線、Docker、sandbox provisioning、LLM providers 或 event delivery，因此不要把它當成唯一的 readiness signal。

請參閱 [GitHub 上維護的 PM2 ecosystem file](https://github.com/geminixiang/mikan/blob/main/deploy/pm2/ecosystem.config.cjs) 與 [Sandbox 模式](/zh-tw/sandbox/) 以瞭解各模式的需求。
