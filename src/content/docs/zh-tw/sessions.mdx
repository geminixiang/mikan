## 平台工作階段模型

Session key 要嘛是單獨的 `conversationId`，要嘛是代表 scoped session 的 `conversationId:suffix`。suffix 就是該平台用來識別 thread 或 reply 對象的值。

| 平台     | `sessionKey` 規則                                                                                                   | 備註                                                                        |
| -------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Slack    | top-level 與 DM：`channelId`；thread（包含 DM 中的 thread）：`channelId:threadTs`                                   | thread sessions 是由近期聊天歷史 bootstrap 的固定檔案                       |
| Discord  | DM 與 shared top-level：`channelId`；thread：`parentChannelId:threadChannelId`；reply：`channelId:repliedMessageId` | guild thread 以其 parent channel 加上該 thread 自己的 id 定址               |
| Telegram | private chat：`chatId`；shared top-level：`chatId:messageId`；shared reply：`chatId:repliedMessageId`               | 沒有原生 thread model，因此被回覆的那則訊息就是 scope                       |
| GitHub   | `GH_<owner>_<repo>_<number>`                                                                                        | 一個 issue 或 pull request 就是一個扁平 session，包含 inline review threads |

## Session key 與 office

Session key 維持原始平台值——`src/sessions/session-key.ts` 中的文法從不接觸 office key。Runtime 狀態是以該對話的 office 加上它的 session key 來定址，因此兩個共用同一個 raw conversation id 的平台，絕不可能選到對方的 runner、queue 或 stop 狀態。儲存路徑則跟著 office 走：session 檔案位於 `<workspace>/<officeKey>/sessions/`。

## 工作階段身分安全

session key 一律只屬於單一對話。平台 adapter 可以提供 scoped key，但對話 intake 與 runtime 會拒絕 conversation prefix 與傳入對話不符的 key。Conversation identity 與 scoped suffix 也會在影響 session 儲存之前，拒絕 path separator、control character，以及特殊的 `.` / `..` segment。Thread session files 維持既有的檔名與持久化行為；sessions 模組還會拒絕 symlink session target，並確保衍生路徑仍留在該 office 的 `sessions/` 目錄之內。

## Thread 血緣

Scoped session 會在自己的 header 中，以 `parentSession`（路徑）與 `parentSessionId`（uuid）記錄它是從哪個 top-level session 建立出來的。這個連結在 reset 後仍會保留：重設一個 scoped session 會重建它的檔案，但保留原本的 parent，而不是重新綁定到現在當下的 top-level session。在血緣 metadata 出現之前寫下的 session 會被原樣保留，不會被重建。

## Bootstrap、rotation、Clean session 與 Dream

新的 scoped session 最多會以過去 14 天內、符合條件的 200 則平台訊息初始化。Shared channel 的 top-level session 以每兩週一次的星期日邊界輪替。Rotation 採 lazy 機制而非 cron：跨過邊界後，第一則符合條件的訊息抵達時，mikan 才會檢查目前 session 的 timestamp。

`/new` 會立即建立 **Clean session**。Biweekly rotation 也只切換 active session file。兩者都不會摘要前一個 session、執行 Dream、等待記憶處理，或刪除舊 JSONL 檔案；既有 conversation `MEMORY.md` 仍獨立可用。

**Dream** 是由系統排程的 office maintenance。台灣時間 02:00–05:00 期間，mikan 會檢查每個已登錄的 Conversation office；當最新 evidence 已閒置五小時後，Dream 會一次處理該 office 所有 top-level、rotated、thread 與 event sessions 新累積的 settled entries。成功後會先完整取代 conversation `MEMORY.md`，再推進 host-private 的 per-session checkpoint；沒有新 evidence 時不會呼叫 model。

產生的 **Memory anchor** 是精簡且可修訂的導向資訊，不是最終真相。較新的 conversation evidence 優先。可變的外部狀態必須在回答當次從 Live source 或 current API 驗證；若來源無法使用，mikan 應說明目前無法驗證，而不是把 memory 當成當前真相。

<Aside type="tip" title="保留可稽核紀錄">
  在 private chat 中使用 `new` / `/new` 可立即重新開始。除非手動移除，先前的 session files
  仍會留在磁碟上供檢查。
</Aside>
