## 平台工作階段模型

Session key 要嘛是單獨的 `conversationId`，要嘛是代表 scoped session 的 `conversationId:suffix`。suffix 就是該平台用來識別 thread 或 reply 對象的值。

| 平台     | `sessionKey` 規則                                                                                                   | 備註                                                                        |
| -------- | ------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| Slack    | top-level 與 DM：`channelId`；thread（包含 DM 中的 thread）：`channelId:threadTs`                                   | thread sessions 是由近期聊天歷史 bootstrap 的固定檔案                       |
| Discord  | DM 與 shared top-level：`channelId`；thread：`parentChannelId:threadChannelId`；reply：`channelId:repliedMessageId` | guild thread 以其 parent channel 加上該 thread 自己的 id 定址               |
| Telegram | private chat：`chatId`；shared top-level：`chatId:messageId`；shared reply：`chatId:repliedMessageId`               | 沒有原生 thread model，因此被回覆的那則訊息就是 scope                       |
| GitHub   | `GH_<owner>_<repo>_<number>`                                                                                        | 一個 issue 或 pull request 就是一個扁平 session，包含 inline review threads |

## Session key 與 office

Session key 維持原始平台值——`src/sessions/session-key.ts` 中的文法從不接觸 office key。Runtime 狀態是以該對話的 office 加上它的 session key 來定址，因此兩個共用同一個 raw conversation id 的平台，絕不可能選到對方的 runner、queue 或 stop 狀態。儲存路徑則跟著 office 走：session 檔案位於 sandbox 看不到的 `~/.mikan/conversations/<officeKey>/sessions/`。

## 工作階段身分安全

session key 一律只屬於單一對話。平台 adapter 可以提供 scoped key，但對話 intake 與 runtime 會拒絕 conversation prefix 與傳入對話不符的 key。Conversation identity 與 scoped suffix 也會在影響 session 儲存之前，拒絕 path separator、control character，以及特殊的 `.` / `..` segment。Thread session files 維持既有的檔名與持久化行為；sessions 模組還會拒絕 symlink session target，並確保衍生路徑仍留在該 office 的 sessions 目錄之內。session 標頭裡記錄的路徑從不被開啟；父 session 一律以 session id 找出。

## Session 如何開始

每個 office 把所有 session 存在一個 pi-durable SQLite 儲存區：top-level session，以及每個 thread 或 reply 範圍各一個 session。

Thread 從造成它的事情開始。每次 run 會記下觸發它的訊息，log 也會在 run 的回答旁記下那則訊息和執行它的 session。開在某次 run 的回答底下、或開在觸發那次 run 的訊息底下的 thread，會 fork 那次 run：它帶著該 session 到那次 run 結束為止的 context，包含工具呼叫與其輸出，所以 agent 不用重跑指令就能說出指令印了什麼。其他 thread 只帶起點訊息和自己的回覆。在這個行為之前就存在的 thread 維持原本的 context。

Session 自己的回答才是它的記憶。聊天同步會把其他人、其他 bot 的訊息以及 mikan 的通知，以標明發言者的聊天紀錄加入；其他 session 的 run 貼出的回答則留給那個 session。更早的歷史仍可在 `log.jsonl` 查詢，agent 也能用 `history` 工具搜尋同一對話的所有 session 與聊天紀錄，包含工具呼叫與其輸出。

## 維運遷移

`mikan migrate` 會把 0.5.3 的 session 檔匯入該 office 的 `sessions.db`，並把原本的 `sessions/` 目錄移到 `sessions-v3/`；詳見 [State 遷移](/zh-tw/deployment/#state-遷移)。

## Clean session 與記憶

Top-level session 會長期沿用，Pi 的自動 compaction 會讓模型 context 維持在上限內。`/new` 會立即重設 session：模型從空的 context 開始，先前的紀錄仍留在儲存區，`history` 工具與 session view 都讀得到。它不會摘要前一段對話，也不會等待記憶處理；既有 conversation `MEMORY.md` 仍獨立可用。

**Memory capture** 會在知識被說出來的當下就記錄。每次由真人觸發的 run 結束後，mikan 會請 Jev 判斷使用者是否建立了長期知識，例如長期規則、交付偏好、關於系統或流程的持久事實，或是一項更正。若是，對話所用的模型會在 conversation `MEMORY.md` 的 `## Captured knowledge` 底下新增或更新個別條目，並標註擷取日期與來源訊息。排程 event 的 run 會略過，永遠不寫入 workspace 共用記憶；未設定 Jev（`OPENROUTER_API_KEY`）時此功能停用。要更正或移除擷取的條目，和其他記憶一樣請 agent 修改即可。

conversation `MEMORY.md`（**Memory anchor**）由 agent 在 run 中寫入，以及由 Memory capture 在 run 結束後寫入；沒有任何排程會重寫或整理它。它是精簡且可修訂的導向資訊，不是最終真相。較新的 conversation evidence 優先。可變的外部狀態必須在回答當次從 Live source 或 current API 驗證；若來源無法使用，mikan 應說明目前無法驗證，而不是把 memory 當成當前真相。
